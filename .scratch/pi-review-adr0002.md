## 1. 对 ADR-0002 路线 B 及火山首选的立场

### 1.1 赞同路线 B（托管 RTC + 语音 Agent + Go 业务工具）——总体赞同，附一个重要修正

**赞同理由：**

1. **路线 A（旧 PCM 协议上补实时）被否决是正确的，且代码证据比 ADR 写的更硬。** 旧链路是"为单向播放设计"的：后端按 20ms 真实时长推帧（`pkg/tts/streamer.go:75-77`），前端按 `word_complete` 攒整词播放（`audio-controller.js:285-296`）。要在其上做全双工对话，需同时重写采集（现为按住式，`voice-command-controller.js:127`）、传输语义（word 作用域累积）、打断取消（现在完全没有）三层——工作量不小于换 SDK，且每一步都在对抗旧协议的隐含假设。ADR-0002 Options A 表格的判断成立。
2. **"保留业务、重做交互"的切分线画对了。** 词库/FSRS/批改有代码与测试且与交互范式无关（复盘 §3 末行）；ADR-0002 Trade-off Analysis 明确"语言迁移不产生自然交流"，避免了推倒重来的最大陷阱。
3. **对话状态与教学状态分离、工具回调带 request_id/版本幂等（ADR-0002 Trade-off Analysis、复盘 §8）是本项目旧伤的对症药。** 旧系统 `cannot_write→next_word` 的粗暴映射（`intent.go:32-40`）和 DICTATING 超时强推（`session.go:1084-1113`）正是两个状态机混用的产物。
4. **RT-01~RT-10 以"真实可听音频"为验收单位**（复盘 §10 末段"必须记录"清单）直接封死了旧测试的漏洞（`dictation-flow.spec.js:122-135` 无音频也通过）。验收哲学正确。

**重要修正（半反对）：R0 不验证工具调用，把路线 B 最大的集成风险推迟到了 R1。** 复盘 §9 R0 明确"先用 3 个固定教学词"、不接业务工具；工具接入是 R1。但路线 B 的核心卖点恰恰是"Agent 模式 + 工具编排"，而复盘 §7 自己引用了火山文档"部分旧控制接口在端到端模式无效"。如果 R0 用纯闲聊/预置词通过，R1 才发现所选供应商的混合编排工具回调不可靠或不满足幂等语义，R0 的结论就要打折重来。**建议：R0 spike 必须包含至少一个真实工具调用（如 `get_lesson_state` 读 3 个固定词），即便不接真实业务**，用最小代价验证"语音→工具→结果→语音"的完整环。

### 1.2 火山 RTC 首选——有条件赞同，需先过三道闸

**赞同的部分：** 在"用户大概率在中国大陆网络 + 已有火山 TTS 账号经验 + 需要一站式 RTC/ASR/LLM/TTS 减少集成面"的约束下，把火山列为**第一个试的对象**合理；ADR-0002 Decision 同时声明"以用户网络、iPad、打断质量、工具可靠性和真实费用决定最终服务，不使用未经实测的最佳排名"，这个克制是对的。

**反对/警惕的部分：**

1. **"首选"目前建立在未验证的权限假设上。** ADR-0002 Consequences 自己承认"需要新的 RTC/实时语音权限；现有 TTS 凭证不推导出这些权限"，Action Item 1 才写"核实服务权限"。把权限核验放在第一位候选的落地步骤里，而不是定首选的前置条件，是流程倒挂——若火山 RTC/Agent 编排需要企业资质或长审核，首选即刻失效。**权限核验应该是 R0 的第 0 天任务，且要有书面结论。**
2. **对照候选的可测性存疑。** OpenAI Realtime 在用户真实网络（大陆）的可达性未验证（ADR-0002 Options C "访问资格/区域…需确认"）；如果它实际上不可测，"对照"就是空的，决策退化为火山单选。应在 R0 计划里显式记录每个候选"能否实测"，不能测的注明原因，否则选型记录不完整。
3. **儿童语音数据出境/合规完全未讨论。** 未成年人的生物识别信息（声纹属于敏感个人信息）上传第三方云——无论境内境外——在 PIPL 下需要监护人同意等流程。复盘 §7、§8 和 ADR-0002 全文没有一处提及。这不是法律意见，但**它可能直接翻转供应商选择**（境内 vs 境外），必须在 R0 前由所有者拍板（见第 4 节 Q3）。
4. **建议补一条供应商抽象要求**：R1 实现业务工具时，把"工具定义→供应商编排"的适配层做成可替换接口，使换供应商的成本被限制在适配层。ADR-0002 目前只说"以实测决定最终服务"，没说决定之后换的成本由谁承担。

- **冻结而非删除**：ADR-0002 Consequences 已定调"旧按住录音及命令分类器只留作历史诊断或备用模式"。落地建议：`/ws` PCM 协议与 `pkg/voice` 命令栈进入**功能冻结**（只修阻塞性 bug，不加新特性），作为 RT-10 要求的降级模式保留（RT-10 明确"备用按钮可用，但界面明确处于降级模式"——按钮路径就是旧页能力的子集）。

### 3.3 里程碑如何重排

维持 R0→R1→R2→R3 主轴（复盘 §9 的顺序逻辑成立：先体验后业务后闭环后容量），做四处补强：

2. **R0 内强制包含一个最小工具调用**（见 1.1 修正），把 T1 风险前移。
3. **R0 设 timebox 与 kill criteria**：每候选建议 ≤2 周真机验证；连续两个候选不达标即回到所有者层面重新裁决（进第 4 节 Q1），而不是无限换供应商。
4. **R2 明确吸收旧 Phase 10**（家长反馈 UI/FEED-01~04）与跨连接恢复（旧 Phase 11 的 ERR-01 残留），R3 吸收旧 Phase 12 与旧代码清理决策——即"旧阶段内容按 R 线重组"，避免两条轨道并行。

## 4. 必须由项目所有者拍板的挑战问题（按重要性排序）

> 以下问题按"不回答就无法推进"的程度排序，供拷问式讨论使用。

1. **产品底线与 kill criteria**：如果 R0 在真实 iPad/网络上实测，RT-04（P95≤2.5s）和 RT-05（打断 P95≤500ms）就是达不到——你接受哪一个：调低标准继续、换供应商再试（最多几家/多久）、还是产品退回"高质量听写+按钮控速"并公开承认语音目标不可行？（复盘 §9 明令禁止"延长等待或改按钮过关"，但不达标时的正路目前没有答案，见 F5。）
2. **供应商权限的现实答案**：火山 RTC + 语音 Agent 编排到底能不能用当前账号类型开通？需要什么资质、几天审核？月度语音云费用上限是多少？（ADR-0002 Action Item 1 只有"核实"二字，无结论前"首选火山"是悬空的，见 1.2-1。）
3. **儿童语音数据的合规底线**：孩子的语音上传到第三方云（境内火山 / 境外 OpenAI），你是否接受？需要监护人同意界面和留存策略吗？这会直接决定候选名单——你现在有答案吗？（全文零覆盖，见 2.2-P 合规、3.4-10。）
4. **旧栈的冻结边界**：R0–R3 期间旧听写页、`/ws` 协议、语音命令栈是完全冻结（只修阻塞 bug），还是继续接需求？单人开发者同时养两条交互栈的代价你认吗？（见 3.2；RT-10 只要求按钮降级可用，不要求旧语音命令继续演进。）
5. **业务线是否暂停**：旧 Phase 10（家长反馈 UI）等内容是等 R2 一并做，还是现在并行推进？（STATE.md frontmatter 仍是 phase 09 executing，见 F1——不明确表态，下一次会话就会默认续做旧轨道。）
6. **验收裁决规则**：RT-01~RT-10 部分通过部分不通过时谁裁决、依据什么？允许调标准吗？调一次标准要不要留痕并重测？（"建议标准"缺裁决机制就成了弹性标准，见 F5。）
7. **R0 的时间盒**：R0 从什么时候开始、总共给几周？每个候选最多试多久？超过预算就升级到你重新决策——你接受这个约束吗？（见 3.3-3。）
8. **教学法的真实偏好**："沉默=写字不自动跳词""求助先提示而非直接跳词"（RT-06，推翻 `intent.go:32-40` 现行为）——这是你和孩子的真实偏好吗？最长愿意等孩子多久不动？（不确认就把状态机改一遍，回头又是一次 8-23 式返工。）
9. **供应商锁定与退出成本**：R1 的业务工具适配层要不要强制做成可换供应商的抽象（多花实现成本）？还是接受火山锁定、换供应商时重写编排层？（见 1.2-4。）
10. **规划文档重构的执行时机**：第 3.1 节列的 STATE/ROADMAP/REQUIREMENTS 修正由谁、在 R0 开始前完成？（这是几小时内的工作，但不做，F1–F4 会持续制造"惯性续旧轨"的风险。）
