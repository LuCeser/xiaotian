# Priority Framework: Fast Feedback Cycle First

**Status**: Accepted

**Context**: 项目已完成3个阶段的基础设施（WebSocket、Python桥接、配置系统），但缺少用户价值实现（前端、TTS、音频处理）。各组件独立工作但无法验证端到端流程是否通畅。开发者感觉项目"失控" — 做了大量工作但无法快速验证想法。

**Decision**: 建立"快速反馈周期优先"的项目优先级框架：

1. **快速反馈周期优先** — 任何阻碍快速验证想法的事情都是最高优先级
2. **本地调试环境** — 必须能本地快速验证改动，而不是推到VPS测试
3. **端到端可见性** — 必须能看到完整的用户流程能跑起来，而不是各组件独立工作

**Rationale**: 
- 开发者无法忍受"写代码 → 推VPS → 部署 → 看效果"的慢速反馈循环
- 没有端到端流程，无法验证整个系统是否能真正工作
- 完美的基础设施如果不能服务用户价值，就是在沙滩上盖楼

**Consequences**: 
- 即将实施极简前端来验证技术栈连通性（打开网页 → WebSocket连接 → 发消息 → 收回复）
- 未来的技术决策都要通过"这是否加快了反馈周期"的检验
- 在最小端到端流程跑通之前，暂停纯基础设施的优化

**Considered Alternatives**:
- **继续完善基础设施** — 被拒绝，因为已经足够支持最小端到端流程
- **直接构建完整听写会话** — 被拒绝，因为违反"快速反馈"原则，需要太多时间才能看到效果
