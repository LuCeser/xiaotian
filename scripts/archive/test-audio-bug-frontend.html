Bug #3: THE REAL BUG - Global Frame Collection Without Word ID Filtering!

Location: test-interface.html line 1024

function handleAudioFrame(payload, sequence) {
    // ... sequence validation ...

    // Collect frames for HTMLAudioElement playback
    if (playback.active && payload.length === AudioFrameSize) {
        // ❌ BUG: NO CHECK THAT THESE FRAMES BELONG TO THE REQUESTED WORD!
        playback.audioBuffer.push(new Uint8Array(payload));
    }
}

🐛 ROOT CAUSE:

  1. Frontend calls playWord(0) for "hello" → sends {word_id: "hello", session_id: "session-123"}
  2. Backend starts streaming "hello" audio frames with sequences 1,2,3...
  3. BUT if there's ANY buffering, cross-connection, or if the backend accidentally sends multiple words' frames...
  4. The frontend collects ALL frames with playback.active=true, regardless of which word they belong to!

THERE IS NO WORD ID VALIDATION IN THE FRONTEND!

The frontend trusts that playback.active=true means "collect frames for the right word", but it doesn't verify that incoming frames actually belong to the requested word.

Bug #4: No Word ID in Audio Frames Protocol

Architecture Issue: The WebSocket protocol sends audio frames with sequence numbers, but doesn't include word ID identification!

// Frame header structure (pkg/ws/protocol.go):
type FrameHeader struct {
    Version    uint8
    MsgType    uint8    // 0x01 = Audio
    Sequence   uint32   // ❌ NO WORD ID!
    Timestamp  uint32
    PayloadLen uint16
    Reserved   uint16
}

PROBLEM: When streaming multiple words in a session, there's no way for the frontend to distinguish which word a frame belongs to. If frames from multiple words are in flight, the frontend can't filter them.

🎯 Most Likely Root Cause

Based on the symptoms ("plays all words instead of one") and the code analysis, the most likely causes are:

  1. Backend sequence numbering issue: Streamer.go line 115 uses currentSeq := uint32(i + 1). If multiple StreamWord calls overlap or if there's a concurrency bug, sequences might collide.
  2. Missing word ID validation: Frontend blindly collects all frames when playback.active=true without checking if they belong to the requested word.
  3. Prefetch cross-contamination: The prefetch system loads all words, and there might be a bug where StreamWord reads the wrong word's PCM data.

CRITICAL MISSING PIECE: The WebSocket protocol should include word ID in audio frames, or the backend should send a clear "word_start" marker before streaming each word's audio.

✅ Recommended Fixes

  1. Frontend defense: Stop collecting frames after receiving word_complete status frame for the current word.
  2. Backend fix: Ensure StreamWord atomically loads and streams only ONE word's PCM, with clear boundaries.
  3. Protocol enhancement: Add word ID to audio frame headers, or send explicit start/end markers.
  4. State machine: Frontend should track "awaiting word", "receiving frames", "playing audio" states explicitly.
