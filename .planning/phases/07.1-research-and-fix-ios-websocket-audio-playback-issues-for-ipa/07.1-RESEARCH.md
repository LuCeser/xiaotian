# Phase 07.1: Research and Fix iOS WebSocket Audio Playback Issues - Research

**Researched:** 2026-08-09
**Domain:** iOS Safari Web Audio API + Go WebSocket binary frame protocol bug fixes
**Confidence:** HIGH

## Summary

Phase 07.1 修复 iPad Safari 上的 WebSocket 流式 TTS 播放问题，使其满足最小端到端听写流程：**学生打开网页 → 一次点击解锁 → 系统朗读 20-30 个单词（无缝连续） → 学生语音回答 → 显示反馈**。

CONTEXT.md 已锁定高层策略（Web Audio API 取代 HTMLAudioElement、16kHz AudioContext、一次点击解锁、无缝调度、保留 WS 传输、修复 sequence-number bug）。本次研究的核心任务不是重新论证这些决策，而是为 planner 提供具体落地的细节：

1. **验证 D-02 前提成立**：iOS Safari 14.5+（WebKit r267014, bug 216425）确实支持 `new AudioContext({ sampleRate: 16000 })`，WebKit 在硬件采样率（通常 48000 Hz）与请求采样率不一致时内部实例化 `MultiChannelResampler` + `PushPullFIFO`，`AudioContext.sampleRate` 会正确返回请求的 16000。**D-02 假设成立**——前端应始终使用 `ctx.sampleRate` 创建 AudioBuffer，绝不能硬编码 16000。
2. **强化 D-03 解锁模式**：iOS Safari 17+ 的 AudioContext 解锁需要**三个**条件同时成立，CONTEXT.md 只提到两个：(1) `ctx.resume()` 必须在用户手势回调中同步调用（无 await）；(2) **必须在手势回调中同步 `source.start(0)` 一个真实 AudioBufferSourceNode**——光调用 `resume()` 即使 `ctx.state === 'running'` 输出也会被静音；(3) 用 `touchend`/`click`/`keydown`/`mouseup`，**禁用 `touchstart`**（miniaudio#759 实测 iOS 17 上 `touchstart` 导致静默解锁失败）。
3. **D-09 已在代码中强制执行**：`pkg/ws/server.go:135` 已有 `EnableCompression: false` 注释明确标注 Safari 兼容性。规划阶段只需新增一条断言测试确保后续 PR 不回归。
4. **定位三个协议 bug 的精确行号**：`streamer.go:88-97`（startSeq 语义混乱）、`streamer.go:115`（`currentSeq := uint32(i+1)` 每个单词重置）、`handlers.go:357`（`Sequence: 1` 硬编码 TODO）。
5. **绘制前端集成点旧→新映射**：`test-interface.html` 1591 行，需要替换 5 个核心函数 + 1 个状态对象。

**主要建议：** 实现顺序应是（a）先修后端协议 bug（D-10/D-11/D-12），写回归测试；（b）重写前端 playback 层为 Web Audio API，保留 WS plumbing；（c）真 iPad UAT。**绝对不要在 protocol bug 未修复前调 Web Audio**——否则前端调试时无法区分是音频调度问题还是 sequence 重复问题。

### Pattern 1: Gapless AudioBuffer Scheduling（web.dev "A Tale of Two Clocks"）
**What：** 在 audio clock（`ctx.currentTime`）上预调度下一个 AudioBuffer，而非用 `setTimeout` 触发 `play()`。
**When to use：** 任何需要无缝连续播放的场景——本阶段 20-30 个单词串播是核心需求。
**Example：**
```javascript
// Source: https://web.dev/articles/audio-scheduling（CONTEXT.md specifics 已引用）
let nextStartTime = audioCtx.currentTime;  // 音频时钟，单调递增

function scheduleWordBuffer(audioBuffer) {
  const source = audioCtx.createBufferSource();
  source.buffer = audioBuffer;
  source.connect(audioCtx.destination);
  // 关键：在 nextStartTime 调度，而非 source.start()（立即）
  source.start(nextStartTime);
  nextStartTime += audioBuffer.duration;
  // 调度后立即释放 source 引用；它会被 GC
  source.onended = () => { /* 可选：用于 UI 反馈，不用于调度下一个 */ };
}

// 欠载恢复：若 nextStartTime 落后 currentTime 太多（>1 个 word 时长），重置
function underrunRecovery() {
  if (nextStartTime < audioCtx.currentTime) {
    nextStartTime = audioCtx.currentTime;  // 丢弃过期的 schedule，对齐当前
  }
}
```

### Pattern 2: iOS Safari 三段式手势解锁（强化 D-03）
**What：** iOS 17+ 上 AudioContext 解锁需要三件事同时做，缺一不可。
**When to use：** "Start Session" 按钮 onclick（D-03 已锁）。
**Example：**
```javascript
// Source: https://github.com/AmaHermes/solar-strike-redux/commit/fbd48e68567064927589c6485dcda0664f9c5fc0
//         + https://github.com/kek/modem/commit/793145ef1ada3482c77e8a30f5ac738481fa8835
//         + miniaudio#759（touchstart 在 iOS 17 必须移除）
function unlockOnGesture() {
  // (1) 必须同步创建（不能 await）
  if (!audioCtx) {
    const AC = window.AudioContext || window.webkitAudioContext;
    audioCtx = new AC({ sampleRate: 16000 });  // D-02
  }
  // (2) resume() 同步调用，不能 await
  audioCtx.resume();  // iOS 看 call-stack 内是否有 user gesture

  // (3) 必须在 gesture 内调度一个真实 buffer，否则 ctx.state='running' 但输出被静音
  const silentBuf = audioCtx.createBuffer(1, 1, audioCtx.sampleRate);
  silentBuf.getChannelData(0)[0] = 0;
  const silentSource = audioCtx.createBufferSource();
  silentSource.buffer = silentBuf;
  silentSource.connect(audioCtx.destination);
  silentSource.start(0);  // ← 这一行是 iOS 解锁的真正钥匙

  // 注意：监听 touchend/click/keydown/mouseup，不要监听 touchstart（D-03 已锁，miniaudio#759 实测）
}

// 在 Start Session 按钮上挂：
startBtn.addEventListener('click', () => {
  unlockOnGesture();  // ← 必须是 onclick 同步第一行
  startSession();     // 真正的业务逻辑
});
```

### Pattern 3: PCM Int16 → Float32 AudioBuffer 转换（D-05）
**What：** 后端发 s16le PCM，前端需转 Float32 才能写入 AudioBuffer。
**Example：**
```javascript
// D-05 已锁。注意 sampleRate 用 ctx.sampleRate，绝不硬编码 16000。
function pcmInt16ToAudioBuffer(pcmBytes /* Uint8Array of s16le */) {
  const numSamples = pcmBytes.length / 2;
  // ⚠️ 用 ctx.sampleRate 而不是 16000——iOS Safari 14.5+ 会用请求的 16000，
  // 但代码必须假设 ctx.sampleRate 可能与 PCM 采样率不同并做适配（见 Pitfall 2）
  const audioBuffer = audioCtx.createBuffer(1, numSamples, audioCtx.sampleRate);
  const channelData = audioBuffer.getChannelData(0);
  const view = new DataView(pcmBytes.buffer, pcmBytes.byteOffset, pcmBytes.byteLength);
  for (let i = 0; i < numSamples; i++) {
    channelData[i] = view.getInt16(i * 2, true) / 32768;  // little-endian s16le
  }
  return audioBuffer;
}
```

### Pattern 4: 会话级单调 sequence 计数器（修复 D-11）
**What：** 替换 `currentSeq := uint32(i + 1)` 的 per-word 重置为会话/stream 级单调计数。
**Example：**
```go
// 推荐方案：Streamer 持有 sessionID → uint32 计数器的 map（或 stream-level 字段）
type Streamer struct {
    // ... 既有字段
    seqCounters   map[string]uint32  // key: sessionID, value: next seq
    seqCountersMu sync.Mutex
}

func (s *Streamer) nextSeq(sessionID string) uint32 {
    s.seqCountersMu.Lock()
    defer s.seqCountersMu.Unlock()
    s.seqCounters[sessionID]++
    return s.seqCounters[sessionID]
}

// 在 StreamWord 循环中：
for i := startIndex; i < len(frames); i++ {
    currentSeq := s.nextSeq(sessionID)  // ← 替代 uint32(i + 1)
    // ... 其余逻辑不变
}
```

### Anti-Patterns to Avoid
- **`source.start()` 不传时间参数 → 立即播放而非无缝衔接：** 必须传 `nextStartTime`，否则每次都从 `currentTime` 开始 → 单词间产生 ~tens of ms 静音 gap。
- **用 `setTimeout` 调度播放：** 主线程计时器在 iOS 后台/标签切换时漂移几十到几百 ms，导致欠载或重叠。**只能用 `ctx.currentTime`**。
- **`await ctx.resume()` 放在 onclick 第一行：** 任何 await 都会切断 user-gesture call-stack，iOS 静默拒绝。`resume()` 不 await，后续业务可以 await。
- **监听 `touchstart` 触发解锁：** iOS 17 上 `touchstart` 时手指还在屏幕上，WebKit 不认为手势完成 → 静默失败。必须 `touchend`/`click`。
- **硬编码 `16000` 作为 AudioBuffer sampleRate：** 即使 D-02 假设成立，代码仍应读 `ctx.sampleRate`；万一未来 iOS 版本回归或硬件强制 48000，代码不会崩。
- **保留 `playback.audioBuffer[]` + `setTimeout(playCollectedAudio, 300)` 的 300ms-gap-detection 模式：** 这是 HTMLAudioElement 时代的产物，与 Web Audio API 的 word_complete 事件触发模式冲突。新方案应在 `word_complete` 立即调度，不要 timer。

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PCM → AudioBuffer 转换 | 自己写采样率重采样（线性插值等） | 直接用 `ctx.createBuffer(1, N, ctx.sampleRate)` + 假设 ctx.sampleRate===PCM rate；万一不一致用 WebKit 内建 MultiChannelResampler（即让 ctx 在 16000 创建） | D-02 已让 ctx 在 16kHz 创建，WebKit 自动处理重采样 `[VERIFIED: WebKit r267014]` |
| Audio scheduling | 自己写 `setTimeout` 排队 | `source.start(nextStartTime)` + audio clock | setTimeout 在 iOS 切后台时漂移 `[CITED: web.dev/articles/audio-scheduling]` |
| 用户手势解锁 | 自己写 "请点击启用声音" 提示 | silent buffer source.start(0) in onclick | iOS 唯一可靠方案 `[VERIFIED: solar-strike-redux commit fbd48e6]` |
| CRC-16 校验 | 已经实现，不要重写 | `crc16Checksum()`（`test-interface.html:473`）+ `pkg/crc16` | 已锁定 `[VERIFIED: pkg/ws/codec.go:13]` |
| WAV 文件封装 | 保留 `createWavFromPCM16`（仅用于 fallback "Test Audio Element" 按钮） | Web Audio API 不需要 WAV 封装——直接 PCM→AudioBuffer | 删除新 playback 路径中的 WAV 步骤 |

**Key insight：** iOS Safari 的 Web Audio API 14.5+ 已经把所有"难"的部分（采样率转换、调度、混音）内建了。本阶段最大的反模式是想"控制"太多——让 `ctx.sampleRate` 自己处理采样率、让 `source.start(when)` 自己处理调度、让 `MultiChannelResampler` 自己处理转换。前端代码只需做三件事：(1) 在手势内创建+resume+start silent；(2) 收到 word_complete 把累积 PCM 转 AudioBuffer；(3) 用 `nextStartTime` 调度。

**The canonical question：** *本次重写后，浏览器/服务端还有什么旧状态残留？* 答案：浏览器端——若用户在重写部署前已打开页面，旧 JS 全局变量仍存活，但页面 reload 后清空，无需迁移。服务端——`seqCounters` map 必须有清理钩子，否则 100 并发下每个 session 泄漏 ~40 字节累积成 4KB——可接受但有卫生问题。

## Common Pitfalls

### Pitfall 1: iOS Safari AudioContext 解锁后仍然静音
**What goes wrong：** 调用了 `ctx.resume()`，`ctx.state === 'running'`，但播放任何声音都听不到。
**Why it happens：** iOS Safari 17+ 还要求在手势回调内**同步调度一个真实 AudioBufferSourceNode**（即使是 1-sample silent buffer）。光 `resume()` 不够。CONTEXT.md 的 D-03 提到了这点但描述不够强——本次研究在 `solar-strike-redux` commit fbd48e6 中验证为**强制必须**。
**How to avoid：** 在 "Start Session" 按钮 onclick 第一行调用 Pattern 2 的 `unlockOnGesture()`，里面 `silentSource.start(0)` 不可缺。
**Warning signs：** `ctx.state` 显示 running 但播放无声；Desktop Safari 能听到 iPad 听不到。

### Pitfall 2: 硬编码 sampleRate 16000 写入 AudioBuffer 导致播放变速
**What goes wrong：** 如果 iOS 在某些边界场景（如蓝牙耳机接入、特定 iOS 版本）让 `ctx.sampleRate` 返回 48000，而代码用 `ctx.createBuffer(1, N, 16000)` 写 PCM 数据，会触发隐式重采样或播放变速。
**Why it happens：** 虽然 D-02 假设 iOS 14.5+ 会用请求的 16000，但研究显示 iOS 在某些硬件场景（如外接 DAC、AirPods 接入）会切换 hardwareSampleRate，context 可能重新协商。
**How to avoid：** **永远用 `ctx.sampleRate` 创建 AudioBuffer，绝不能硬编码 16000**。同时记录一行警告日志：`if (ctx.sampleRate !== 16000) console.warn('ctx rate mismatch:', ctx.sampleRate)`——为真机调试提供信号。
**Warning signs：** 音调偏高（变速 → pitch shift）；单词播放时长与预期不符。

### Pitfall 3: `touchstart` 在 iOS 17 上解锁失败
**What goes wrong：** 在 `touchstart` 事件回调里调用 `resume()` 不生效，但同样的代码在 `touchend` 或 `click` 里有效。
**Why it happens：** iOS 17 WebKit 收紧了 autoplay 策略，认为 `touchstart` 时手势"未完成"（手指还在屏幕），不满足 user-gesture 条件。`miniaudio#759` 已确认。
**How to avoid：** 监听 `touchend` / `click` / `keydown` / `mouseup`，**禁用 `touchstart`**。CONTEXT.md D-03 已锁此方向。
**Warning signs：** 首次点击无声，第二次点击有声（首次 touchstart 失败，第二次 touchend 成功）。

### Pitfall 4: `await ctx.resume()` 切断手势调用栈
**What goes wrong：** React/Vue 异步组件或 `async function` 处理 onclick 时，第一个 `await` 之后 iOS 不再认 user gesture，`resume()` 静默失败。
**Why it happens：** iOS 判断 user-gesture 是基于同步调用栈。任何 `await`（包括 `await ctx.resume()` 本身）都会把后续代码移到 microtask 队列，失去 gesture 上下文。`kek/modem` commit 793145e 专门为此重写。
**How to avoid：** `unlockOnGesture()` 必须是**普通函数**（非 async），内部不 await。后续业务逻辑可以 async。
**Warning signs：** 简单 onclick 有效，复杂组件无效；console 显示 `The AudioContext was not allowed to start`。

### Pitfall 5: 会话级 sequence 计数器在 session cleanup 时不清理
**What goes wrong：** Pattern 4 推荐的 `seqCounters map[string]uint32` 在 session 结束时不 delete，长期运行下内存泄漏。100 并发 × 4 字节 ≈ 400 字节/批，看似小，但 1C1G VPS 下累积到几小时会触发 RES-01 内存预算告警。
**Why it happens：** Streamer 不知道 session 何时结束——它只接收 `(ctx, client, sessionID, wordID, startSeq)`，没有 cleanup 回调。
**How to avoid：** 暴露 `Streamer.ClearSeqCounter(sessionID)`，在 `pkg/session/Manager` 的 session 销毁钩子（Phase 7 已有）里调用。
**Warning signs：** pprof 显示 `pkg/tts.Streamer.seqCounters` map 持续增长。

### Pitfall 6: 旧的 300ms-gap-detection timer 与新 word_complete 事件冲突
**What goes wrong：** 重写 playback 时如果保留 `setTimeout(playCollectedAudio, 300)` 模式（`test-interface.html:1083-1088`），300ms timer 可能在 word_complete 到达后才触发，导致同一个 PCM 被调度两次或调度时机错乱。
**Why it happens：** HTMLAudioElement 时代没有可靠的"单词结束"信号，前端用 300ms 无新帧作为代理。新协议有显式的 `word_complete` status frame（`streamer.go:144-184`），timer 模式冗余且有害。
**How to avoid：** 删除整个 `playback.playTimer` 路径，仅由 `handleStatusFrame` 收到 `type:'word_complete'` 时触发调度。
**Warning signs：** 同一单词播放两次；日志显示 frame 在 word_complete 之后到达（即旧的 bug detector 触发）。

### Pitfall 7: WS permessage-deflate 在 Safari 17.6 上杀连接（D-09 已防）
**What goes wrong：** 服务端发 TEXT 控制帧后紧跟一个 ≥2KB 的 BINARY 音频帧，若 `permessage-deflate` 协商成功，Safari 17.6 抛 "Protocol error" 断连。
**Why it happens：** Apple 的 `client_no_context_takeover` 实现长期有 bug（uWebSockets#1347、Apple forum 744018 都确认）。
**How to avoid：** D-09 已锁——保持 `EnableCompression: false`。`pkg/ws/server.go:135` 已实现。**仅需要加一条回归测试断言 upgrader 配置不变**。
**Warning signs：** 连接建立后几秒内断开，Safari console 显示 "Protocol error"；Chrome 正常。

```javascript
    playback.audioBuffer.push(new Uint8Array(payload));

```

新逻辑（Web Audio API）：
```javascript
function handleAudioFrame(payload, sequence, wordId) {
  // sequence dedup（修复 D-11 后只需简单单调检查）
  if (sequence <= lastSeq) { duplicateCount++; return; }
  if (sequence > lastSeq + 1) { gapCount++; addLog('Gap detected', 'audio'); }
  lastSeq = sequence;

  // 累积 PCM 到对应 wordId
  if (!pendingPcm.has(wordId)) pendingPcm.set(wordId, []);
  pendingPcm.get(wordId).push(new Uint8Array(payload));
}
```

### Example 3: 替换 `handleStatusFrame` + `playCollectedAudio`（`test-interface.html:990-1134`）

新逻辑（在 word_complete 触发调度）：
```javascript
function handleStatusFrame(payload) {
  const data = JSON.parse(decodeText(payload));
  if (data.type !== 'word_complete') return;

  const chunks = pendingPcm.get(data.word_id);
  pendingPcm.delete(data.word_id);
  if (!chunks || chunks.length === 0) return;

  // 合并 PCM
  const totalLen = chunks.reduce((s, c) => s + c.length, 0);
  const pcmBytes = new Uint8Array(totalLen);
  let off = 0;
  for (const c of chunks) { pcmBytes.set(c, off); off += c.length; }

  // 转 AudioBuffer（Pattern 3）
  const numSamples = pcmBytes.length / 2;
  const buf = audioCtx.createBuffer(1, numSamples, audioCtx.sampleRate);
  const view = new DataView(pcmBytes.buffer, pcmBytes.byteOffset, pcmBytes.byteLength);
  const chan = buf.getChannelData(0);
  for (let i = 0; i < numSamples; i++) {
    chan[i] = view.getInt16(i * 2, true) / 32768;
  }

  // 调度（Pattern 1）
  const src = audioCtx.createBufferSource();
  src.buffer = buf;
  src.connect(audioCtx.destination);
  if (nextStartTime < audioCtx.currentTime) nextStartTime = audioCtx.currentTime;  // underrun recovery
  src.start(nextStartTime);
  nextStartTime += buf.duration;
}
```

### Example 4: 后端 `sendControlFrame` 修复（D-12，`handlers.go:347-363`）

旧（硬编码）：
```go
header := &ws.FrameHeader{
    Version:    1,
    MsgType:    msgType,
    Sequence:   1, // TODO: per-handler atomic counter  ← 当前现状
    PayloadLen: uint16(len(jsonBytes)),

```

新（per-handler 原子计数器）：
```go
// 全局或 per-Server 的原子计数器（最简单方案：包级 var）
var controlFrameSeq uint32 // atomic

func sendControlFrame(client *ws.Client, msgType ws.MessageType, payload interface{}) error {
    jsonBytes, err := json.Marshal(payload)
    if err != nil { return err }
    header := &ws.FrameHeader{
        Version:    ws.ProtocolVersion,        // 用常量替代魔数 1
        MsgType:    msgType,
        Sequence:   atomic.AddUint32(&controlFrameSeq, 1),  // ← 单调
        PayloadLen: uint16(len(jsonBytes)),
    }
    return client.Send(ws.EncodeFrame(header, jsonBytes))
}
```

   - What we know：D-13 要求真机 UAT，但未指定 iOS 版本。
   - What's unclear：iOS 16 vs 17 vs 18 在 unlock 细节、AudioContext sampleRate 边界、visibility 行为上有差异。

3. **D-16（20ms ticker vs 整词 PCM 批量）是否要在本阶段决定？**
   - What we know：CONTEXT.md 标记为 planner discretion。
   - What's unclear：保留 ticker 对前端 Web Audio API 无害（前端按 word_complete 触发，不关心帧节奏）；删除 ticker 可减少 CPU。
   - Recommendation：**保留 ticker 不动**，本阶段只修 sequence bug。删除 ticker 是独立优化，避免与本阶段混淆。

## Security Domain

> Config.json `workflow` 未显式设 `security_enforcement: false`，按默认 enabled 处理。本阶段主要是客户端音频与既有 WS 协议，ASVS 适用范围有限。

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | 本阶段不动 auth（WS 升级时已有 user_id query 参数，Phase 2 决定） |
| V3 Session Management | partial | session cleanup 钩子要清 seqCounters（防内存泄漏 → 可用性攻击面）；ASVS V3.x 不直接适用，属资源卫生 |
| V4 Access Control | no | 不动授权逻辑 |
| V5 Input Validation | yes | WS binary frame 的 CRC-16 已强制（`pkg/ws/codec.go`）；前端 `JSON.parse` status frame 要 try/catch（已有 `test-interface.html:993`） |
| V6 Cryptography | no | 不引入新加密；CRC-16 是完整性校验非密码学 |
| V7 Errors & Logging | yes | `sendControlFrame` 等已有 logger.Warn；新加的 seq counter 不应有信息泄漏 |
| V8 Data Protection | no | PCM 音频不属敏感数据；session_id 已是 UUID |
| V12 Files & Resources | partial | SessionCache PCM 文件清理（Phase 6 已有）；本阶段不动 |

### Known Threat Patterns for iOS Safari + WS Binary Audio

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| 恶意客户端发非 PCM 数据触发 AudioBuffer 异常 | Tampering | `payload.length === AudioFrameSize` 校验（已有 `test-interface.html:1051`）+ CRC-16 header 校验（不覆盖 payload，但 `pkg/ws/codec.go:97` 限制 audio frame 必须 640B） |
| DoS via 大量 session 创建导致 `seqCounters` 泄漏 | Denial of Service | Pitfall 5：`Manager` cleanup 钩子调 `Streamer.ClearSeqCounter`；100 并发硬上限（Phase 1 已有） |
| iOS Safari 解锁提示被钓鱼 | Social Engineering | 不适用——解锁是用户主动点击 "Start Session"，无第三方介入 |
| WS 帧注入（伪造 sequence） | Tampering | CRC-16 header 校验 + D-11 修复后前端按 sequence 单调性检测 gap（已有 `test-interface.html:1031`） |
