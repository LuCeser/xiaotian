## Research Used

Two librarian research sessions dispatched for iOS Safari audio playback architecture:

- **lib-1** (ses_01f91a4ecffegnAZqqbSRp9DpX): dispatched for iOS Safari autoplay policy, Web Audio API, MSE, HTTP progressive, WebSocket binary, AudioWorklet research. Returned EMPTY result.
- **lib-2** (ses_01f8e17f0ffeSPqn6RQk82i5lq): fresh retry with identical research questions. Returned comprehensive 7-section evidence-based report.

**lib-2 key findings (informed D-01..D-09):**
- Web Audio API (AudioContext + scheduled AudioBufferSourceNode) is the clear winner — exact architecture of production iOS TTS/voice apps (readest, runtypelabs/persona). Raw PCM native input, gapless scheduling via audio clock.
- AudioContext at 16kHz supported iOS 14.5+. Prevents WebKit linear-resampler boundary clicks.
- One-tap unlock: `touchend`/`click` (NOT `touchstart` on iOS 17+) + `resume()` + 1-sample silent buffer in-gesture. Persists for page session (foreground).
- `interrupted` state after backgrounding — handle via `visibilitychange`/`statechange`; app-switch needs new gesture.
- MSE REJECTED: W3C registry has no raw PCM; would need PCM→AAC transcoding + fragment muxing.
- HTMLAudioElement chaining REJECTED: not truly gapless (decoder-flush gaps).
- WebSocket binary fine on iOS Safari. Do NOT enable compression — Safari 17.6 text-then-binary deflate bug kills connection. gorilla/websocket defaults OFF.
- AudioWorklet available but unnecessary for pre-generated clips — deferred.
- Latency ~50-250ms total, far under 1.5s budget.
