# Phase 07.1: Research and Fix iOS WebSocket Audio Playback Issues - Context

**Gathered:** 2026-08-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Research and fix iOS/iPad Safari WebSocket audio playback so that the minimum end-to-end dictation flow works on real iPad hardware: **student opens page → one-tap unlock → system reads words → gapless continuous playback of 20-30 words → student responds → feedback**. The existing backend WS audio pipeline stays; the fix is primarily frontend (Web Audio API replacing HTMLAudioElement buffering) plus protocol-correctness bug fixes. This phase delivers a working, tested-on-real-iPad fix — not a research-only recommendation document.

</domain>

<decisions>
## Implementation Decisions

### iOS Audio Playback Strategy
- **D-01:** Use **Web Audio API (AudioContext + scheduled AudioBufferSourceNode)** for audio playback on iPad Safari. Replaces the current HTMLAudioElement buffer-whole-word-then-click-to-play approach. This is the architecture used by production iOS TTS/voice apps (readest, runtypelabs/persona).
- **D-02:** Create `AudioContext` at **16kHz sample rate** (`new AudioContext({ sampleRate: 16000 })`) to match the backend PCM format — supported on iOS 14.5+, prevents WebKit linear-resampler boundary clicks between chained buffers.
- **D-03:** **One-tap gesture unlock pattern:** on first `touchend`/`click`/`keydown` handler (NOT `touchstart` — iOS 17+ requires the tap to complete), call `ctx.resume()` AND immediately start a 1-sample silent `AudioBufferSourceNode` synchronously in the gesture handler. This unlocks AudioContext for the entire page session. The "Start Session" button serves as this unlock tap.
- **D-04:** **Gapless scheduling pattern:** maintain `nextStartTime` on the audio clock; for each word's AudioBuffer, `source.start(nextStartTime); nextStartTime += buffer.duration;`. On underrun, snap `nextStartTime` back to `ctx.currentTime`. Use lookahead 1-2 words. Timing MUST use `ctx.currentTime` (audio clock), never `Date.now()`/`setTimeout`.
- **D-05:** **PCM → AudioBuffer conversion:** received Int16 PCM frames → `Float32Array` (sample / 32768) → `ctx.createBuffer(1, numSamples, 16000)` → write to `channelData[0]`.
- **D-06:** **Visibility/resume handling:** listen to `visibilitychange` and AudioContext `statechange`; on return from background/tab-switch, call `ctx.resume()`. If it rejects (post app-switch requires new gesture), show a "tap to resume" overlay. This is an edge case for short dictation sessions but must be handled.
- **D-07:** **REJECTED alternatives** (with reasons for downstream reference):
  - MSE (MediaSource Extensions): ❌ Cannot play raw PCM (W3C registry only defines fMP4/AAC/MP3); would require server-side PCM→AAC transcoding + fragment muxing — excessive complexity, zero benefit.
  - HTMLAudioElement chaining: ❌ Not truly gapless (decoder-flush gap + ended→play() scheduling delay tens of ms between clips).
  - HTTP progressive download as primary transport: ⚠️ Viable as a fallback only (HTMLAudioElement progressive playback works but isn't gapless; per-element gesture unlock separate from AudioContext unlock).

### Audio Transport Channel
- **D-08:** **Keep WebSocket binary streaming** as the audio transport. Do NOT migrate audio to HTTP. Research confirms iOS Safari WS binary frames work correctly with no inherent latency/buffering issues.
- **D-09:** **Do NOT enable WebSocket compression** (`permessage-deflate`). Safari 17.6 has a confirmed bug where text-frame-then-binary-frame with deflate enabled kills the connection with "Protocol error". Go gorilla/websocket defaults to compression OFF — verify it stays off.

### Protocol Bug Fixes (fix regardless of playback strategy)
- **D-10:** **Fix streamer.go startSeq off-by-one** (`pkg/tts/streamer.go` ~lines 88-97): `if startSeq > 0 { startIndex = startSeq - 1 }` contradicts its own comment. Correct the semantics so breakpoint-resume (if ever used) indexes correctly.
- **D-11:** **Fix per-word sequence number restart:** currently each `StreamWord` call resets `currentSeq = i+1` from 1. Replace with a **session-level (or stream-level) monotonic sequence counter** so frames across multiple words never collide on sequence numbers. This is the root cause of the frontend dedup bug (currently papered over by clearing `receivedSequences` on each new word).
- **D-12:** **Fix sendControlFrame Sequence:1 hardcoded value** (`cmd/service/handlers.go` TODO): use a per-handler atomic counter or session-level counter so control frames also have monotonic sequence numbers.

### Verification Method
- **D-13:** **Real iPad device testing** (user has hardware). Success criteria:
  - One-tap unlock works on first "Start Session" tap; no per-word click required.
  - First audible word latency < 1.5s from session_ready.
  - 20-30 word continuous playback is gapless (no silence gaps, no stuttering, no missed words).
  - App-switch recovery: after returning from background, tap-to-resume overlay appears and playback resumes.
- **D-14:** Desktop Safari + Responsive Design Mode (iPad) can be used for rapid iteration, but final acceptance MUST be on the real iPad device.

### Phase Scope and Deliverables
- **D-15:** **Research + implement fix** (not research-only). Deliver a working end-to-end iPad Safari dictation flow on real hardware. Changes span frontend (Web Audio API rewrite of playback) and backend (protocol bug fixes). Frame format protocol (16-byte header + payload) stays UNCHANGED.

### the agent's Discretion
- **D-16:** Whether to keep the 20ms ticker pacing in `streamer.StreamWord` or batch entire-word PCM into fewer/larger frames. With Web Audio API, the frontend creates one AudioBuffer per word and schedules it — the 20ms per-frame pacing is no longer needed for real-time playback. The planner may simplify the streamer to send whole-word PCM in one or a few frames, reducing frame count and CPU overhead. Frame FORMAT stays unchanged regardless.
- **D-17:** Whether to consolidate the multiple test HTML pages (test-interface.html, test-interface-debug.html, test-audio-sequence-bug.html, debug-test.html) into a single clean page, or keep test-interface.html as the active page and clean up the others. Planner decides.
- **D-18:** Exact underrun recovery strategy (snap to currentTime vs. small lookahead buffer). Planner decides based on testing.
- **D-19:** Whether to keep SpeechRecognition (webkitSpeechRecognition) as-is or adjust its iPad timeout handling. Not in scope of the audio playback fix unless testing reveals it's blocking.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **WS connection + CRC verification** (`test-interface.html`): `connectWS()`, `handleMessage()` binary frame parsing, CRC-16-CCITT verification, `receivedSequences` dedup — keep the WS plumbing, replace the playback layer.
- **`pkg/tts/streamer.go` `StreamWord`**: PCM loading (prefetch map → SessionCache disk), `SliceToFrames`, frame encoding loop. The core frame-sending logic is reusable; the pacing/sequence logic needs the bug fixes (D-10, D-11).
- **`pkg/ws/` frame protocol**: `EncodeFrame`, `FrameHeader`, message type constants — fully reusable, no changes needed.
- **SessionCache + PrefetchNext**: pre-generated PCM cache on disk, prefetch of first 10 words — reusable as-is.

### Established Patterns
- **Frame protocol (16-byte header):** version + msgType + sequence(uint32 BE) + timestamp + payloadLen + reserved + crc16. LOCKED — do not change format.
- **Hybrid dual-mode contract:** control frames (MsgTypeControl JSON) + audio frames (MsgTypeAudio binary PCM) + status frames (MsgTypeStatus JSON like `word_complete`). This phase operates within this contract.
- **Async goroutine per play_word:** `handlePlayWord` launches a goroutine and returns immediately — this pattern stays.

### Integration Points
- **Frontend → Web Audio API:** `test-interface.html` (or replacement) `handleMessage()` for MsgTypeAudio frames currently pushes to `playback.audioBuffer[]` + 300ms gap detection + WAV wrapping. Replace with: collect frames per word → on `word_complete` status frame, convert accumulated PCM → one AudioBuffer → schedule on AudioContext.
- **Backend protocol fixes:** `pkg/tts/streamer.go` (startSeq, sequence counter), `cmd/service/handlers.go` (sendControlFrame sequence) — isolated changes within existing functions.

</code_context>

<deferred>
## Deferred Ideas

- **AudioWorklet for true sample-by-sample streaming:** Available on iOS 14.5+ but unnecessary for this phase (pre-scheduled AudioBuffers suffice). Back-pocket for a future "true real-time streaming" phase if sub-100ms first-word latency becomes a requirement.
- **HTTP progressive download as a fallback/alternative transport:** Viable but not gapless. Only revisit if Web Audio API proves problematic on specific iOS versions during testing.
- **Background audio playback / NowPlaying integration:** Not needed for short interactive dictation sessions. Would require `navigator.audioSession.type = "playback"` (iOS 17+) — deferred.
- **Bluetooth audio latency optimization:** Internal iPad speakers are the primary target. AirPods/BT adds 100-300ms latency — acceptable but not optimized for in this phase.
- **Consolidating test HTML pages into a proper frontend app:** This phase fixes audio playback; a proper frontend architecture (React/Vue/Svelte) is a separate future phase per CONTEXT.md ("Frontend: ❌ Completely missing").

</deferred>
