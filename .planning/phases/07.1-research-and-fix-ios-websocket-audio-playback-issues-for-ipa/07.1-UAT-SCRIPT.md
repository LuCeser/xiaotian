> **Phase:** 07.1-research-and-fix-ios-websocket-audio-playback-issues-for-ipa · Plan 04 Task 1 (auto) → Task 2 (human-verify gate)

> **What is being tested:** the Plan 03 frontend rewrite — one-tap 3-condition iOS unlock, PCM→AudioBuffer gapless scheduling on the audio clock, and app-switch tap-to-resume recovery — over the backend protocol fixes (Plans 01+02, monotonic sequence contract).

> **D-13 success conditions (verbatim):**
> 1. One-tap unlock works on first "Start Session" tap; no per-word click required.
> 2. First audible word latency < 1.5s from `session_ready`.

> 4. App-switch recovery: after returning from background, tap-to-resume overlay appears and playback resumes.

## 0. Pre-flight

### P-1 — Serve `test-interface.html` so the iPad can reach it

The Go service itself serves the page. From the repo root (`D:\workspace\ai\xiaotian`):

```powershell
go run ./cmd/service -config config.yaml
```

- The public mux serves `test-interface.html` at BOTH `/` and `/test-interface.html` (`cmd/service/main.go` `publicMux`).
- The service listens on **`0.0.0.0:8080`** (`config.yaml` → `server.addr`), i.e. all interfaces — any device on the same LAN (or the VPS public address) can reach it. `/health` stays on `127.0.0.1:8081` (irrelevant to the UAT).
- The page derives its WebSocket target from its own host (`window.location.hostname + ':8080'`, `test-interface.html:607-608`) — so loading via the LAN IP makes it connect to `ws://<LAN-IP>:8080/ws`, not the iPad itself.

**iPad URL (open in iPad Safari):**

```
http://<host-LAN-or-VPS>:8080/test-interface.html
```

or simply `http://<host-LAN-or-VPS>:8080/`.

- **LAN path (recommended for this UAT):** find the host's IPv4 on the same network as the iPad — Windows: `ipconfig` → IPv4 Address of the active Wi-Fi/Ethernet adapter; Mac: System Settings → Network. If the dev machine is the iPad's WiFi hotspot host, use the hotspot's gateway IP. Then open `http://192.168.x.x:8080/test-interface.html` on the iPad.
- **VPS path (if the iPad is not on the dev machine's LAN):** deploy/run the same binary on the VPS (already listening on `0.0.0.0:8080`) and open `http://<vps-ip-or-host>:8080/test-interface.html`.

> **⚠️ CRITICAL — do not skip: whitelist the iPad's Origin.** `ws.allowedOrigins` defaults to `["localhost", "127.0.0.1"]` (`pkg/infra/config.go:628`). When the iPad loads `http://192.168.x.x:8080`, Safari sends `Origin: http://192.168.x.x:8080`, which does NOT match the default whitelist → the WS upgrade is silently rejected: the page loads but the status stays disconnected. Add the host's LAN IP (or VPS host) to `config.yaml` (a port-less entry suffices — `CheckOrigin` strips the port, `pkg/ws/server.go:149-158`):

```yaml
ws:
  allowedOrigins: [localhost, 127.0.0.1, 192.168.1.50]
```

Restart the service after editing `config.yaml`. A connection check is built into Condition 1.

**Sanity check that the service is up** (from the dev machine): `curl http://127.0.0.1:8080/test-interface.html` returns the HTML page; the console log line `public server listening addr=0.0.0.0:8080` appears at boot.

> **D-14 note:** do NOT substitute Desktop Safari Responsive Design Mode for this gate. RDM cannot reproduce the iOS unlock, the `interrupted` state after backgrounding, or post-app-switch gesture requirements (`07.1-RESEARCH.md` §Environment Availability). RDM is an iteration aid only.

## 1. Condition 1 — One-tap unlock (D-13 #1)

> *"One-tap unlock works on first 'Start Session' tap; no per-word click required."*
> **Mechanism under test:** `unlockAudioContext()` runs as the FIRST synchronous statement of the Start Session tap (`onclick="unlockAudioContext(); startSession()"`) — constructs `AudioContext({sampleRate:16000})`, calls `resume()` with no await, and `silentSource.start(0)`s a 1-sample silent buffer, all inside the gesture. No `touchstart` listener exists.

**Steps:**
1. On the iPad, open `http://<host-LAN-or-VPS>:8080/test-interface.html`.
2. Tap **Connect** → confirm the WS status goes connected (the `allowedOrigins` whitelist from P-1 is working).
3. Tap **Start Session** **exactly once**.
4. Confirm audio begins — do NOT tap anything else. Per-word clicks must never be needed for the whole session.

**Result:**
- [ ] PASS — audio began after the single Start Session tap, no second tap required
- [ ] FAIL — audio did not start / needed an extra tap
- Observations: `__________________________________________________`

**⚠️ Watch for these warning signs (RESEARCH Pitfalls):**
- **Pitfall 1 — state running but silent:** `audioCtx.state` shows `running` and the page logs "unlocked", yet nothing is audible. Means the silent-buffer `start(0)` arm of the unlock is missing/broken (D-03 condition 3) — sound output is muted despite `running`.
- **Pitfall 3 — first tap silent, second tap audible:** exactly this symptom indicates a `touchstart`-style unlock bug (iOS 17+ treats the gesture as incomplete while the finger is down). The fix is the `touchend`/`click`-driven unlock already wired in the rewrite.
- **Pitfall 4 — `await` cut the gesture stack:** console shows `The AudioContext was not allowed to start`; the unlock function must remain non-async.

## 3. Condition 3 — Gapless 20-30 word playback (D-13 #3)

> *"20-30 word continuous playback is gapless (no silence gaps, no stuttering, no missed words)."*
> **Mechanism under test:** `word_complete`-driven scheduling (D-04) — each word's PCM is converted to one AudioBuffer and `source.start(nextStartTime)`'d on the audio clock, then `nextStartTime += buf.duration`; an underrun snaps `nextStartTime` back to `ctx.currentTime` (D-18). Timing never uses `Date.now()`/`setTimeout`.

**Steps:**
1. Let the full session play through (typically 20-30 words; queue via the page's Play/Play All flow after Start Session — per D-13 condition 1 there must be NO per-word clicking).
2. Listen for **silence gaps** between words, **stuttering**, or **missed words** (a word that never sounds).
3. Note the word count that actually played and any word the page logs as scheduled but that was inaudible.

## 4. Condition 4 — App-switch recovery (D-13 #4)

> *"App-switch recovery: after returning from background, tap-to-resume overlay appears and playback resumes."*
> **Mechanism under test:** `visibilitychange` → `audioCtx.resume()` on return to visible (auto-resume if iOS kept the context alive); `audioCtx.onstatechange` shows a full-screen **tap-to-resume overlay** when the context is not `running`, and the overlay's own tap re-runs `unlockAudioContext()` then hides itself.

**Steps:**
1. Start playback (session must be mid-play — e.g. after Conditions 2-3 have words queued).
2. Switch Safari to the background (home button or home-gesture swipe up).
3. Wait a few seconds (enough for iOS to suspend audio / set `interrupted`).
4. Return to Safari (App Switcher or Safari icon).
5. Confirm playback resumes by EITHER path:
   - **Path A — auto-resume:** audio continues on its own (`ctx.resume()` succeeded on return; no overlay needed), OR
   - **Path B — tap-to-resume:** the tap-to-resume overlay appears; tapping it (a fresh user gesture) re-runs the 3-condition unlock and playback resumes.

**Result:**
- [ ] PASS — playback recovered via **Path A (auto-resume)**
- [ ] PASS — playback recovered via **Path B (tap-to-resume overlay + tap)**
- [ ] FAIL — neither path recovered playback (stays silent even after tapping the overlay)
- Path observed: `A / B` (circle one) — observations: `__________________________________________________`

**⚠️ Watch for:** the page logging `[AUDIO] AudioContext not running — tap-to-resume overlay shown` without an overlay appearing (UI bug), or an overlay that appears but a tap does not restart audio (re-unlock broken).
