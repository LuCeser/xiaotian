later phases use for typed database access. SessionRepository owns Go's
session/session_events writes; CardRepository is read-only access to the
Python-owned cards table (the only sanctioned Go read path, used by Phase 5 FSRS
orchestration).

(Python canonical) and D-03-a (write separation) at the type level — there is
simply no write method to call. This is the data-access slice Plan 05 wires into
main.go.

reusing the newTestDB helper from Plan 03.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repository caller → SQL layer | Untrusted input (ids, unit strings) crosses into parameterized queries |
| Go read path → Python-owned cards table | Read-only boundary; writes prohibited by type design |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Tampering | SQL injection via repository params | high | mitigate | all queries use database/sql ? placeholders; typed method params (int64/string), never raw SQL fragments (RESEARCH Security Domain) |
| T-04-10 | Tampering | Go writes to Python-owned cards table | high | mitigate | CardRepository interface has NO write methods; compile-time guarantee — grep for INSERT/UPDATE/DELETE in card_repo.go is zero (D-01/D-03-a) |
| T-04-11 | Information Disclosure | Parsing fsrs_card leaks/ duplicates FSRS logic | medium | mitigate | Card.FsrsCard is a raw string; encoding/json is not imported for it; Go uses pybridge for typed FSRS fields (RESEARCH Pitfall 5) |
| T-04-12 | Tampering | SELECT * hides schema drift | medium | mitigate | explicit column lists fail loudly on Python-side column changes (RESEARCH Pitfall 4) |
</threat_model>
