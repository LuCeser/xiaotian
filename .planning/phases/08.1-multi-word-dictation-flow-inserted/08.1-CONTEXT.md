<domain>
## Phase Boundary

Phase 8.1 **wires the end-to-end multi-word dictation playback** — student taps
"I want to dictate 30 words" → the backend sequentially streams all words with
real-time progress → the session completes. It closes the integration gap
between the backend multi-word FSM (Phase 7) and the student frontend (Phase 8).

Concretely this phase makes the backend **drive the whole word loop** after
`start_session` (auto-advance): start word 0, stream each word's audio, advance
word-by-word emitting `progress_update` + `word_complete`, and emit
`session_complete` on the last word. The frontend is already built as a passive
consumer for exactly this flow and requires only one small wiring addition
(setting `currentWordId`).

**In scope:**
- Backend: auto-advance the session FSM through the word queue (word-0 start +
  between-word advance + last-word completion), emitting `progress_update`,
  `word_complete`, `session_complete`.
- Backend: propagate `word_id` so the frontend can route audio frames.
- Frontend: set `currentWordId` from the new `progress_update.word_id` field
  (unblocks the audio-controller frame-drop).

**Out of scope:**
- Parent review/rating UI and FSRS rating updates (Phase 10, per Phase 7 D-12).
- WebSocket reconnection / session resume (Phase 11 — owns Phase 8 UAT test 7).
- Any frontend re-architecture (no framework, no build step — 1C/1G VPS).
- New audio playback logic (Phase 07.1 Web Audio pipeline stays as-is).

</domain>

<decisions>
## Implementation Decisions

All decisions below were produced by the pi design advisor (deepseek-v4-pro,
`--thinking high`) via Orca dispatch, then **confirmed by the user** ("全部采纳").
Full option-by-option rationale (A/B/C with codebase grounding) is in
`08.1-DESIGN-ANALYSIS.md` — read it before planning.

### Orchestration model (the flagged open decision)
- **D-01: Backend auto-advance (server-driven), NOT client-driven.** After
  `start_session`, the backend owns the entire word loop — it streams word 0,
  and after each word's `WordComplete` it auto-advances to the next word with
  **no client round-trip**, until the queue is exhausted. The frontend sends
  only `start_session` and otherwise passively consumes
  `session_ready`/`progress_update`/`word_complete`/`session_complete`. —
  **Reversibility:** one-way — once the FSM + emission logic is built around
  server-driven advancement, reverting to client-driven would require changing
  both the FSM and re-adding frontend `play_word`/`next_word` senders that
  currently do not exist. Rationale: this merely *implements* Phase 7 D-13
  ("system-driven auto-transition is the v1 choice for student simplicity"),
  which had been decided but not yet wired through to a working multi-word loop.

### FSM change for auto-advance
- **D-02: Extend the `transition()` table with `DICTATING + WordComplete`.** Add
  one case: on `EventWordComplete` in `StateDictating`, if `wordIndex` is the
  last → `StateWaitingParent`; else `wordIndex++` → `StateListening` (which
  `onTransition` already turns into a `spawnStreamWord` for the next word). Keep
  `transition()` a pure state-machine function (it already mutates `wordIndex`
  for `next_word`, so this fits the existing pattern). Do NOT add a new event
  type and do NOT bypass the FSM from the event loop.
- **D-03: Word-0 auto-start (planner must nail down).** `handleStartSession`
  (`cmd/service/handlers.go:173-205`) currently sends `session_ready` and
  returns, leaving the session in `IDLE` waiting for a client `play_word` that
  never comes. For the auto-advance model, the backend must auto-start word 0
  after `session_ready` — either by pushing an internal `play_word`/start event
  onto the session channel from `handleStartSession` (or `Manager.NewSession`),
  or by auto-transitioning `IDLE→LISTENING` at session `Start()`. The existing
  `IDLE + play_word → LISTENING` transition (fsm.go:44) is reused; only the
  *trigger* changes from client-sent to backend-internal. The planner picks the
  cleanest trigger site. This is part of D-01, called out separately because the
  pi analysis's FSM sketch covered between-word advance but not the initial
  start.

### `currentWordId` propagation (resolves the audio frame-drop)
- **D-04: Add an optional `word_id` field to the `progress_update` control
  frame; the frontend sets `currentWordId` from it.** The frontend must know the
  word's ID **before** that word's audio frames arrive (audio-controller keys
  per-word PCM by `wordId` and drops frames when it's falsy —
  `audio-controller.js:157-159`). Backend emits `progress_update` (carrying
  `currentWord`, `completedWords`, and now `word_id`) at each word boundary
  *before* streaming that word's audio. Frontend `websocket-client.js
  _applyProgressUpdate` (line 467) extends to
  `setState({ currentWordId: frame.word_id || getCurrentWordId() })`. The field
  is backwards-compatible (absent → keep prior value). — **Reversibility:**
  costly — adding a field to a frame payload touches the backend emitter, the
  frame struct, and the frontend handler, but is additive (no migration).

### Gapless multi-word playback timing
- **D-05: Rely on immediate auto-advance streaming for v1; defer prefetch.**
  After `WordComplete`, the event loop transitions to `LISTENING` and
  `spawnStreamWord` starts the next word's `StreamWord`. This is in-memory +
  TTS-cached (SessionCache already prefetches the first 10 words), so the
  inter-word delay should be sub-second vs >1s word durations → gapless on the
  07.1 audio clock. Do NOT build pipelining/prefetch now; only revisit
  (e.g. a background `PreloadWord(nextWord)`) if real-iPad profiling reveals an
  audible gap. The Phase 07.1 D-13 real-hardware gapless bar is the acceptance
  target.

### `session_complete` + post-session UI
- **D-06: Emit `session_complete` when the FSM enters `WAITING_PARENT` after the
  last word.** Add an `onTransition` handler for `StateWaitingParent` that sends
  `session_complete{totalWords}`. The frontend's existing
  `_applySessionComplete` (`websocket-client.js:515`) already sets
  `sessionActive:false`, `status:'FEEDBACK'`, `completedWords:total`, which
  `ProgressDisplay` renders as 100% + "🎉 Great job!". Do NOT introduce a new
  terminal state and do NOT skip `WAITING_PARENT` — it is the correct
  Phase 8→10 handoff point (parent review is Phase 10's job).

### Planner's Discretion
- The exact trigger site for word-0 auto-start (D-03): internal event from
  `handleStartSession`/`Manager.NewSession` vs auto-transition at `Start()`.
- The exact Go struct/field layout for the `progress_update` payload + the
  `word_id` source (`wordQueue[wordIndex]` — confirm whether the word string or
  a stable id is the routing key; the frontend treats it opaquely).
- Whether `progress_update` is emitted from `onTransition` (on entering
  `LISTENING`) or alongside `spawnStreamWord`. Either is fine as long as the
  frame precedes that word's audio frames.
- Test strategy (table-driven FSM transition tests mirroring the existing
  `fsm_test.go` style; a backend integration test asserting the frame sequence
  `session_ready → (progress_update → audio* → word_complete)×N →
  session_complete`).

## Existing Code Insights

### Reusable Assets
- **Frontend control-frame dispatcher** (`websocket-client.js handleControlFrame`)
  — already implements `session_ready`/`progress_update`/`word_complete`/
  `session_complete` handling AND triggers audio playback on `word_complete`.
  This phase adds zero new frontend frame types; only one `setState` line in
  `_applyProgressUpdate` (to set `currentWordId`).
- **Frontend progress UI** (`ProgressDisplay`) — already renders the progress
  bar, word counter, and FEEDBACK→100%+"🎉"; just never receives advancing
  `progress_update`s. No UI work needed.
- **Backend session event loop** (`session.go run`/`onTransition`/`spawnStreamWord`)
  — the auto-advance mechanism reuses `spawnStreamWord` (already called on
  entering LISTENING); D-02 just adds the DICTATING→LISTENING auto-transition.
- **`sendControlFrame` helper** (`handlers.go:362`) — the canonical emitter for
  control/status frames; reuse for `progress_update`/`session_complete`.
- **TTS SessionCache prefetch** — first 10 words already cached on disk, so
  back-to-back `StreamWord` calls are fast (supports D-05 gapless claim).

### Established Patterns
- **Flat typed-enum switch FSM** (Phase 7 D-03) — `transition()` is a pure
  state-machine function; D-02 extends it within this pattern (no new event
  type, no FSM lib, no state-pattern abstraction).
- **System-driven transitions via the `word_complete`/`WordComplete` signal**
  (Phase 7 D-13) — `StreamWord` completion → `EventWordComplete` → FSM advance.
  D-01/D-02 are the completion of this pattern across the whole word queue.
- **Channel-based single-writer event loop** (Phase 7 D-02) — all FSM mutations
  happen in the session goroutine via `transition()`; emission happens in
  `onTransition()`. New emissions (progress_update, session_complete) follow
  this seam.
- **Frame protocol (16-byte header) is LOCKED** — no header changes; new fields
  go in the JSON control-frame payload only (D-04).

### Integration Points
- **handleStartSession → session auto-start** (D-03): after sending
  `session_ready`, push the initial word-start into the session (internal event
  or auto-transition). This is the one new wiring site on the backend accept
  path.
- **onTransition → emit hooks** (D-04, D-06): on entering `LISTENING` emit
  `progress_update` (with `word_id`); on entering `WAITING_PARENT` emit
  `session_complete`.
- **_applyProgressUpdate → setState({currentWordId})** (D-04): the one frontend
  wiring addition, unblocking `app.js:235` + `audio-controller.handleAudioFrame`.

<specifics>
## Specific Ideas

- The dominant intent (pi advisor + user): the backend becomes the **single
  driver** of the word loop. The student frontend is a pure renderer/player —
  it never requests a word, it only plays what arrives and reflects progress.
  This matches the elementary-school-student UX (one tap, then just listen) and
  the 07.1 gapless-audio architecture (pre-schedule whole-word buffers on the
  audio clock; per-word client round-trips would reintroduce gaps).
- The expected backend→frontend frame sequence for a full session:
  `session_ready` →
  (`progress_update{currentWord, completedWords, word_id}` → audio frames… →
  `word_complete{word_id}`) × N → `session_complete{totalWords}`.
- Acceptance is the Phase 07.1 D-13 real-iPad bar: one-tap start, gapless
  20–30 word playback, progress advancing word-by-word, clean completion.

</specifics>
