## 1. What Phase 8.1 must deliver

**Goal (from ROADMAP.md §Phase 8.1):** Wire the end-to-end multi-word dictation
playback — student taps "I want to dictate 30 words" → system sequentially reads
all words with real-time progress → session completes. This **closes the
integration gap** between the backend multi-word FSM (Phase 7) and the student
frontend (Phase 8).

**Success criteria (what must be TRUE):**
1. After `session_ready`, words play sequentially 1→N **without further user interaction**.
2. Real-time progress display advances word-by-word (progress bar 0%→100%, word counter).
3. `session_complete` frame emitted and UI transitions to post-session state.
4. `currentWordId` correctly set so audio frames are not dropped (resolves `audio-controller.js:157-159` frame-drop).
5. Unblocks Phase 8 UAT test 8 (real-time progress display).

**Requirements:** DICT-01 (full), DICT-03, DICT-05 (multi-word), WEB-02 (real-time progress).

**The one explicitly-flagged open design decision (ROADMAP):**
> auto-advance (backend drives the word loop after `start_session`) vs
> client-driven (frontend orchestrates `play_word`/`next_word`).

## 2. The integration gap — ALREADY SCOUTED (verify against the code)

The scout below is authoritative — it was produced by reading every file end-to-end.
**Confirm it by opening the files**, then design within it. Do NOT re-derive from
scratch.

### 2.1 Frontend is FULLY BUILT to receive (passive), but the backend never sends

**`pkg/web/static/js/websocket-client.js` `handleControlFrame` (lines 398–434)**
already dispatches every frame this phase needs to emit:
- `session_ready` → `_applySessionReady` (line 411): sets `sessionActive:true`,
  `status:'DICTATING'`, `words`, `totalWords`, `currentWord:0`, `completedWords:0`.
- `progress_update` → `_applyProgressUpdate` (line 417/467): sets `currentWord` +
  `completedWords` (validates numeric, rejects negatives + completedWords>total).
- `word_complete` → `_applyWordComplete` (line 420/498): increments
  `completedWords` AND triggers `window.audioController.playWordComplete(word_id)`.
- `session_complete` → `_applySessionComplete` (line 423/515): `sessionActive:false`,
  `status:'FEEDBACK'`, `completedWords:total`.

**Key architectural signal:** the frontend **triggers audio playback ON
`word_complete`** (line 510) — it does NOT request audio. It is a passive consumer.
There is **no code path in the frontend that sends `play_word` or `next_word`.**

### 2.2 Frontend sends ONLY `start_session`

**`pkg/web/static/js/ui-components.js` `SessionButton.handleClick` (lines 113–158):**
on tap it unlocks audio (`audioController.unlockAudioContext()`, line 134) and sends
exactly one frame:
```js
this.wsClient.send({ type: 'start_session', params: { limit: 30 } });   // lines 145-148
```
It never sends `play_word` or `next_word`. `ProgressDisplay` (same file, lines
279–460) renders progress from state but nothing advances the counters.

### 2.3 `currentWordId` is NEVER set → every audio frame is DROPPED

**`pkg/web/static/js/app.js` `handleMessage` (lines 226–244):** binary audio frames
are routed using `var wordId = state.currentWordId || null;` (line 235), then
`audioController.handleAudioFrame(payload, sequence, wordId)` (line 236).

**`pkg/web/static/js/state-manager.js`:** `currentWordId` initializes to `null`
(`initialState()`, line 62) and **nothing ever calls setState with a currentWordId**.
`getCurrentWordId()` exists (line 224) but has no producer.

**`pkg/web/static/js/audio-controller.js` `handleAudioFrame` (lines 139–166):**
```js
if (!wordId) {
  console.warn('[audio] Frame received with no wordId — ignored ...');   // lines 157-159
  return;   // <-- FRAME DROPPED
}
```
`setCurrentWord(wordId)` exists (line 270) but has **zero callers**. `playWordComplete`
(line 176) merges per-word PCM from `pendingPcm[wordId]` and schedules it on the
audio clock (`scheduledTime`, gapless per 07.1 D-04). So the audio pipeline is
correct *if* frames are routed under the right wordId and `word_complete` fires.

### 2.4 Backend emits NOTHING after `session_ready`, and never starts the loop

**`cmd/service/handlers.go` `handleStartSession` (lines 173–205):** calls
`manager.NewSession(...)` then sends `session_ready` (lines 192–202) and **returns**.
It does NOT push a first `play_word`. There are **0 emit sites** for
`progress_update` and `session_complete` anywhere in `cmd/` or `pkg/`
(confirm: `rg "progress_update|session_complete"` in Go files returns nothing).

### 2.5 Backend FSM: the word-to-word advance is CLIENT-gated

**`pkg/session/fsm.go` `transition` (lines 26–94):**
- `IDLE + play_word` → `LISTENING` (wordIndex=0)  [line 44]
- `LISTENING + WordComplete` → `DICTATING`  (system-driven)  [line 53]
- `DICTATING + next_word` → if last word: `WAITING_PARENT`; else `wordIndex++`, → `LISTENING`  [lines 69-78]

**`pkg/session/session.go`:**
- `onTransition()` (line 343): on entering `LISTENING`, calls `spawnStreamWord()` (line 355).
- `spawnStreamWord()` (line 362): streams `wordQueue[wordIndex].Word`, and on
  return pushes `EventWordComplete` (line 389) → FSM goes `LISTENING→DICTATING`.
- **There is no path from `DICTATING` back to `LISTENING` for the next word
  without a client `next_word` frame.** And the client never sends one (§2.2).

**Net effect:** after `session_ready`, the session sits in `IDLE` forever (no
first `play_word`), and even if it started, it would stall after word 0 (no
`next_word`). The multi-word loop is completely broken end-to-end.

## 3. Gray areas to analyze (produce one section each)

For EACH gray area, your `08.1-DESIGN-ANALYSIS.md` section must contain:
**Options · Codebase grounding (file:line) · Recommendation · "Decision the user must make".**

### Gray Area 1 — Orchestration model: auto-advance (backend-driven) vs client-driven

This is the flagged open decision. Note the frontend (§2.1) already assumes a
**passive/backend-driven** model (plays on `word_complete`, sends no per-word
requests). Phase 7 D-13 (`07-CONTEXT.md`) also chose "system-driven transitions
… client sends high-level intents, not low-level transitions" and DEFERRED
client-driven `word_done` frames ("system-driven auto-transition is the v1
choice for student simplicity"). Weigh:
- **A: Backend auto-advance** — after `session_ready`, backend streams word 0
  immediately; after each `WordComplete`, backend auto-advances to the next word
  (internal event, no client round-trip) until the queue is exhausted, then emits
  `session_complete`.
- **B: Client-driven** — frontend sends `play_word`/`next_word` per word.
- Consider: success criterion #1 ("without further user interaction"), the
  existing passive frontend, 07.1 gapless audio scheduling (frontend pre-schedules
  on the audio clock — per-word round-trips would reintroduce gaps), latency, and
  blast radius on the Phase 7 FSM.

### Gray Area 2 — FSM change for auto-advance (if A is chosen)

How to model backend auto-advance cleanly within `pkg/session`:
- Add a `DICTATING + WordComplete → LISTENING (next)` transition (and last-word
  → `WAITING_PARENT` + emit `session_complete`)? Or
- Inject a synthetic internal `EventAutoAdvance` after `WordComplete`? Or
- Keep `WordComplete` driving `LISTENING→DICTATING→LISTENING` directly?
- Where does `progress_update` get emitted (per word)? Where does `session_complete`
  get emitted (last word)? Ground this in `session.go onTransition()`/`spawnStreamWord()`
  and `fsm.go`. Identify the minimal, FSM-purity-preserving change. Note `transition()`
  is documented as a "pure state-machine function" (fsm.go line 9) — preserve that.

### Gray Area 3 — `currentWordId` propagation (resolves the frame-drop)

The frontend must know which word's audio frames are arriving BEFORE they arrive
(audio-controller keys PCM by wordId; `app.js:235` reads `state.currentWordId`).
Options:
- Backend emits a frame carrying the wordId ahead of each word's audio (e.g.,
  extend `progress_update` with a `word_id` field; or a `word_started`/reuse frame).
- Frontend derives currentWordId from the ordered `words[]` array (set on
  `session_ready`) using `currentWord` index — needs `currentWord` to advance
  BEFORE the word's frames.
- Recommend the option with the least protocol churn, and specify EXACTLY which
  frame field the frontend reads and which `state-manager`/`ws-client` line sets
  `currentWordId`. Cross-check `audio-controller.js handleAudioFrame` and
  `playWordComplete`.

### Gray Area 4 — Gapless multi-word playback timing

07.1 (`07.1-CONTEXT.md` D-04/D-16) scheduled audio on the audio clock
(`scheduledTime`) and pre-schedules whole-word buffers on `word_complete`. For
multi-word, analyze the inter-word gap risk: if the backend serializes
`StreamWord(word_i)` then advances only after completion, word_{i+1}'s PCM may
arrive after word_i finished playing → audible gap. Options:
- Backend prefetches/pipelines the next word's audio while the current plays
  (SessionCache already prefetches first 10 words — see `pkg/tts`).
- Frontend buffers ahead (accumulate word_{i+1} PCM before word_i `word_complete`).
- Tolerate small gaps (20–30 words, short clips).
- Ground in `pkg/tts/streamer.go StreamWord`, `pkg/tts` SessionCache/prefetch, and
  `audio-controller.js` scheduling. Recommend the simplest approach that keeps
  playback gapless on real iPad (07.1 D-13 real-hardware bar).

### Gray Area 5 — `session_complete` + post-session UI transition

Success criteria #3: `session_complete` emitted and UI → post-session state.
- Where emitted (last word → `WAITING_PARENT` or `FEEDBACK`?), what fields
  (`totalWords` per `_applySessionComplete` line 515).
- Does the backend go to `WAITING_PARENT` (waiting for parent review, per
  `fsm.go` line 73) or straight to `FEEDBACK`? Phase 7 D-12 defers all
  rating/feedback to Phase 10. Clarify what "post-session state" means for the
  STUDENT UI now (Phase 10 parent review is out of scope). Recommend the terminal
  state + frame that lets `ProgressDisplay` show 100% + "🎉 Great job!" without
  implying parent-review features that don't exist yet.
