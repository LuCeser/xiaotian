**Dominant architectural shape:**
The student frontend is a passive consumer that receives a sequence of
server-pushed frames (`session_ready` → `progress_update` → `word_complete` →
`session_complete`) and renders progress / plays audio without ever sending
per‑word requests. To close the integration gap, the backend must adopt an
**auto‑advance model** where the session FSM self‑transitions through the word
queue after each word’s audio stream completes — advancing `wordIndex`,
emitting `progress_update` and `word_complete` frames, and finally emitting
`session_complete`. This decision is mandated by Phase 7 D‑13 (system‑driven
transitions) and by the existing frontend architecture, which has no code
path for `play_word` or `next_word`. The change is contained within the Go
session layer and requires a single FSM transition extension plus the addition
of `currentWordId` propagation to unblock the audio pipeline.

---

## Gray Area 1 — Orchestration model: auto-advance (backend-driven) vs client-driven

### Options
- **A – Backend auto‑advance**
  After `session_ready` the backend streams word 0 immediately; after each
  `WordComplete` it auto‑advances to the next word (internal event, no client
  round‑trip). Once the queue is exhausted it emits `session_complete`.
- **B – Client‑driven**
  Frontend issues `play_word`/`next_word` per word, and the backend stays
  in its current FSM that gates advancement on these client frames.

### Codebase grounding
- **Frontend is built to receive, not request**  
  `pkg/web/static/js/websocket-client.js` *handleControlFrame* (lines 398‑434)
  already dispatches `session_ready`, `progress_update`, `word_complete`,
  `session_complete`. It contains **no sender** for `play_word` or
  `next_word`.
- **UI only sends `start_session`**  
  `pkg/web/static/js/ui-components.js` *SessionButton.handleClick*
  (lines 113‑158) sends exactly `{ type: 'start_session', params: { limit: 30 } }`
  and then stops.
- **Backend FSM requires client frames to advance**  
  `pkg/session/fsm.go` *transition* (lines 26‑94): `LISTENING + WordComplete →
  DICTATING`, `DICTATING + next_word → LISTENING (wordIndex++)`. No path
  exists from `DICTATING` back to `LISTENING` without a client `next_word`.
- **Phase 7 D-13 explicitly chose system‑driven transitions**  
  `.planning/phases/07-session-state-management/07-CONTEXT.md` states:
  “Client-driven state transitions (explicit word_done frames) — deferred;
  system-driven auto-transition is the v1 choice for student simplicity.”

### Recommendation
**Option A – Backend auto‑advance.**  
Rationale:
1. The frontend already expects a passive push model — adding client‑driven
   logic would require large UI changes and risk breaking the existing audio
   scheduling.
2. Auto‑advance eliminates per‑word round‑trips, preserving the gapless
   playback achieved in Phase 07.1 (audio‑clock scheduling in
   `audio-controller.js` depends on whole‑word buffers arriving before
   scheduled time; a client round‑trip per word would add latency).
3. Phase 7 D‑13 already settled this as the v1 approach for student
   simplicity; we are merely implementing that decision.
4. The blast radius is confined to the Go session layer; the frontend requires
   zero behavioural changes beyond receiving the new frames.

**Decision the user must make:**  
Confirm that the system will adopt **backend auto‑advance** (Option A).

## Gray Area 2 — FSM change for auto‑advance

### Options
- **A – Add a `DICTATING + WordComplete` transition**
  Extend `transition()` to handle `(StateDictating, EventWordComplete)` and
  either advance to `LISTENING` (next word) or to `WAITING_PARENT` (last word).
  The FSM stays pure; `wordIndex` increment happens inside `transition()`.
- **B – Inject synthetic internal event**
  After `WordComplete` is processed (`LISTENING → DICTATING`), the event loop
  immediately posts a new internal `AutoAdvance` event that drives `DICTATING →
  LISTENING` or `DICTATING → WAITING_PARENT`. This keeps the existing
  `transition` table unchanged but adds a new event type.
- **C – Bypass the FSM for advancement**
  In `session.go`’s event loop, after `spawnStreamWord` completes and pushes
  `EventWordComplete`, check remaining words and call `spawnStreamWord` again
  without a state transition. This is simple but violates FSM purity.

### Codebase grounding
- `pkg/session/fsm.go` *transition* (lines 26‑94): current table supports
  `DICTATING + next_word` → `LISTENING`. The function is documented as a
  “pure state-machine function” (line 9).
- `pkg/session/session.go` *onTransition* (line 343): on entering `LISTENING`
  it calls `spawnStreamWord()` (line 355).
- `spawnStreamWord()` (line 362): streams `wordQueue[wordIndex].Word` and on
  completion pushes `EventWordComplete` (line 389) → FSM processes it as
  `LISTENING → DICTATING`.
- `pkg/session/types.go` / `pkg/session/manager.go`: define `Event*` types
  and route them to the session’s `Push` channel.

### Recommendation
**Option A – Extend the transition table with `DICTATING + WordComplete`.**
Rationale:
- Preserves FSM purity and fits the existing pattern (`transition()` already
  mutates `wordIndex` for `next_word`).
- Minimal addition: one new case in the switch, two branches (next word /
  last word). No new event types, no changes to the event loop dispatch.
- `onTransition()` already handles state entry actions; adding a handler for
  `WAITING_PARENT` (or `FEEDBACK`) to emit `session_complete` is trivial.
- Option B adds a new event type without clear benefit; Option C breaks the
  FSM contract and makes future state debugging harder.

Concrete implementation sketch:
```
case StateDictating, EventWordComplete:
    if wordIndex == last {
        return StateWaitingParent, nil
    }
    wordIndex++
    return StateListening, nil   // triggers spawnStreamWord again
```
In `onTransition`, for `StateWaitingParent`, emit `session_complete`.

**Decision the user must make:**  
Approve extending the FSM with `DICTATING + WordComplete → LISTENING (next) /
WAITING_PARENT (last)` and adding the corresponding `onTransition` emission
logic.

## Gray Area 3 — `currentWordId` propagation (resolves the frame‑drop)

### Options
- **A – Extend `progress_update` with a `word_id` field**
  Backend includes the current word’s ID in every `progress_update` frame.
  Frontend `_applyProgressUpdate` sets `state.currentWordId`.
- **B – Derive `currentWordId` from the ordered `words[]` array**
  On `session_ready`, store the `words` array. On each `progress_update` that
  advances `currentWord`, compute `currentWordId = words[currentWord].id`.
  This avoids a protocol change but ties frontend knowledge to the exact
  session‑ready payload.
- **C – Dedicated `word_started` frame**
  A new frame type (`word_started`) sent right before the audio stream of a
  word, carrying the `word_id`. This is explicit but adds protocol surface.

### Codebase grounding
- `pkg/web/static/js/audio-controller.js` *handleAudioFrame* (lines 139‑166):
  requires `wordId` to key per‑word PCM buffers; drops frames when `wordId` is falsy.
- `pkg/web/static/js/app.js` *handleMessage* (lines 226‑244): reads
  `state.currentWordId` from `state-manager` (line 235).
- `pkg/web/static/js/state-manager.js` *initialState* (line 62):
  `currentWordId: null`. No code ever calls `setState` with a `currentWordId`
  value, and `getCurrentWordId()` has zero callers (line 224).
- `pkg/web/static/js/websocket-client.js` *_applySessionReady* (line 411)
  sets `words`, `totalWords`, `currentWord:0`, `completedWords:0` but not
  `currentWordId`.
- `pkg/web/static/js/websocket-client.js` *_applyProgressUpdate* (line 417/467)
  updates `currentWord` and `completedWords` but not `currentWordId`.

The frontend must know the word’s ID **before** the first binary audio frame
of that word arrives. The backend sends audio frames immediately after
entering `LISTENING` via `spawnStreamWord`. Therefore the `word_id` must be
set either in the frame that triggers the state change to `LISTENING` or in
a frame sent just before streaming starts.

### Recommendation
**Option A – Add `word_id` to the existing `progress_update` frame.**
Rationale:
- The `progress_update` frame is already emitted at word boundaries; adding
  one string field is a minimal protocol change (JSON field, backwards
  compatible if absent).
- The frontend `_applyProgressUpdate` already runs at the right moment — we
  simply extend it to set `state.currentWordId = frame.word_id` (or keep
  existing value if field is missing, for robustness).
- Does not require the frontend to index into the `words` array (which may
  be useful later for other purposes but isn’t needed for this single value).
- Avoids a new frame type (Option C) that would duplicate the progress‑update
  timing.

Implementation:
- Backend: when emitting `progress_update` (in `onTransition` or after
  advancing), include `"word_id": wordQueue[wordIndex].ID`.
- Frontend: in `_applyProgressUpdate`, after line 467 (or inside the
  validated block), call `this.stateManager.setState({ currentWordId: frame.word_id || this.stateManager.getCurrentWordId() })`.

**Decision the user must make:**  
Approve extending `progress_update` payload with an optional `word_id` field
and having the frontend set `currentWordId` from it.

## Gray Area 4 — Gapless multi‑word playback timing

### Options
- **A – Rely on immediate auto‑advance streaming**
  After `WordComplete`, the backend immediately advances and starts streaming
  the next word. The frontend audio‑controller buffers incoming PCM per
  `word_id` and schedules playback seamless via `scheduledTime`.
- **B – Backend prefetch/pipeline the next word’s TTS**
  Use `pkg/tts` SessionCache (already prefetches first 10 words) to start
  streaming the next word before the current word’s audio finishes.
- **C – Frontend buffer‑ahead**
  Frontend requests (or backend pushes) the next word’s audio frames earlier,
  possibly by sending a `progress_update` with `word_id` for the *next* word
  while current word is still playing, so the frontend can pre‑buffer.
- **D – Tolerate small gaps**
  Accept a minor silence between short words (~200‑300 ms) and revisit if
  user feedback indicates it’s noticeable.

### Codebase grounding
- `pkg/session/session.go` *spawnStreamWord* (line 362): runs
  `streamer.StreamWord(word)` in a goroutine; it returns only after the TTS
  stream completes. The next word cannot begin until this goroutine returns
  and the event loop processes `WordComplete`.
- `pkg/tts/streamer.go` *StreamWord*: sends audio chunks via
  `sender.SendBinary()`. No built‑in pipeline for the next word.
- `pkg/tts/types.go`: `SessionStreamer` interface – a `StreamWord` method
  without concurrency guarantees.
- `pkg/tts` SessionCache (prefetch): mentioned in Phase 7.1 context; likely
  caches TTS audio in memory for words, but does it push early? Not wired
  into streaming.
- `pkg/web/static/js/audio-controller.js` *playWordComplete* (line 176):
  merges per‑word PCM and schedules it on the audio clock using
  `scheduledTime` derived from the end of the previous buffer, achieving
  gapless scheduling **provided the whole PCM arrives before the scheduled
  time**.
- `audio-controller.js` *handleAudioFrame* (line 139): adds incoming chunks
  to `pendingPcm[wordId]`. If `word_{i+1}` PCM starts arriving after
  `word_i`’s `word_complete` has already fired, it will still be accumulated
  because `word_complete` for `word_i` triggers scheduling of buffer up to
  that point, but the new word’s first chunks might arrive after scheduling.
  However `playWordComplete` is only called for the completed word; the next
  word’s buffer is built incrementally and later `playWordComplete` for it
  will schedule it. So the question is: does the next word’s entire PCM
  arrive before its own `word_complete` fires? Yes, because `word_complete`
  for `word_{i+1}` will be sent only after `StreamWord(word_{i+1})` finishes,
  meaning all PCM for that word has been sent. So the frontend will have all
  data before the scheduling moment. The risk is the delay between
  `word_complete` of word_i and the start of streaming word_{i+1}. That gap
  may be tens of milliseconds (goroutine spawn, TTS fetch, etc.), but the
  frontend’s `scheduledTime` for word_{i+1} is computed as
  `previousScheduledTime + previousWordDuration`. If the next word’s PCM
  arrives after that scheduled time has already passed, a gap occurs.
  However, typical word durations are > 1 second; the backend delay is
  sub‑second, so likely fine.

### Recommendation
**Option A with a small safeguard:**
Use immediate auto‑advance (as chosen in Gray Area 1) — after `WordComplete`,
the event loop processes the transition, enters `LISTENING` for the next
word, and calls `spawnStreamWord`. This sequence is fast (in‑memory, no I/O
except TTS). If profiling reveals a gap, implement Option B by warming the
next word’s TTS in the cache during the current word’s playback (e.g., a
background `PreloadWord(nextWord)` call). For v1, keep it simple; the
Phase 07.1 real‑hardware bar (iPad, 16 kHz) should be met.

**Decision the user must make:**  
Approve relying on immediate auto‑advance streaming with no additional
prefetching now; defer pipeline/prefetching until observed gaps appear.

## Gray Area 5 — `session_complete` and post‑session UI transition

### Options
- **A – Emit `session_complete` on entering `WAITING_PARENT`**
  Backend FSM transitions to `WAITING_PARENT` after the last word’s
  `WordComplete`. In `onTransition`, when entering `WAITING_PARENT`, send
  `session_complete` to the frontend. The frontend already sets
  `status: 'FEEDBACK'` and renders the congratulations message.
- **B – Emit `session_complete` directly from the FSM and stay in `FEEDBACK`**
  Change the FSM to have a `FEEDBACK` state and transition to it after the
  last word, skipping `WAITING_PARENT` entirely because parent review is
  Phase 10.
- **C – No explicit terminal state; frontend detects `completedWords == totalWords`**
  Avoid a new frame; the frontend simply watches `progress_update` and when
  `completedWords === totalWords`, transitions internally to the “done” UI.
  This requires no backend change but breaks the protocol contract
  (other parts of the app may expect `session_complete`).

### Codebase grounding
- `pkg/session/fsm.go` *transition* (line 73): when `next_word` on last word,
  returns `WAITING_PARENT`. This state exists but is currently unreachable
  because `next_word` is never sent.
- `pkg/session/session.go` *onTransition*: currently handles `IDLE`,
  `LISTENING`, `DICTATING`; there is no handler for `WAITING_PARENT` or
  `FEEDBACK`.
- `pkg/web/static/js/websocket-client.js` *_applySessionComplete* (line 423/515):
  sets `sessionActive: false`, `status: 'FEEDBACK'`, `completedWords: totalWords`.
  The `ProgressDisplay` component (ui-components.js line 279) reads these
  state values and shows 100% + “🎉 Great job!”.
- Phase 7 D-12: “all rating/feedback deferred to Phase 10”. The term
  “post‑session state” for the student UI in v1 just means “session is over,
  show completion”.

### Recommendation
**Option A – Use `WAITING_PARENT` as the immediate trigger for `session_complete`.**
Rationale:
- `WAITING_PARENT` is already defined in the FSM and represents the
  “session finished, awaiting parent action” concept, which fits Phases 8‑10.
  Emitting `session_complete` upon entry cleanly separates the end‑of‑session
  notification from the future parent review flow.
- The frontend already handles `session_complete` correctly and transitions
  to a non‑interactive “FEEDBACK” view — exactly what we want the student to
  see immediately.
- No new states or frames required; only an `onTransition` handler for
  `WAITING_PARENT` that calls `s.sendControlFrame(session_complete{...})`.
- Option B would remove a state that is part of the planned future flow; not
  worth the churn. Option C violates the existing protocol and would require
  the frontend to independently detect completion, which is fragile if
  progress updates are ever skipped.

**Decision the user must make:**  
Approve emitting `session_complete` when the FSM enters `WAITING_PARENT`
after the last word, and keep the frontend’s existing `_applySessionComplete`
handler as the post‑session UI transition.

## Risk / blast‑radius

- **FSM modification (Gray Area 2):** The `transition` function is central to
  session state. A mistake could break existing `LISTENING`/`DICTATING`
  transitions. The change is limited to a single new case and two possible
  target states; it does not alter existing cases. **Mitigation:** keep the
  change minimal and add unit tests for the new transitions.
- **Protocol extension (Gray Area 3):** Adding `word_id` to
  `progress_update` is backwards‑compatible if the field is optional. The
  frontend must handle the case where the field is missing (e.g., in a legacy
  session). **Mitigation:** guard with `frame.word_id ||` fallback.
- **No change to frontend state management shape** — we add a setter call,
  not new state keys, so the risk of UI breakage is very low.
- **One‑way decisions:**
  - Once auto‑advance is in place, reverting to client‑driven would require
    changing both FSM and frontend (removing `next_word` client stubs,
    re‑adding them). The current frontend has no such code, so it’s not a
    regression.
  - Adding `WAITING_PARENT` handler for `session_complete` locks the UI into
    showing “feedback” after every session; but that matches the desired
    student UX.
- **Checkpoint:** After the user confirms the decisions herein, the
  downstream planner should treat the answers as locked and produce a
  `PLAN.md` with concrete tasks. A `checkpoint:decision` is warranted for the
  FSM change and the protocol field addition.
