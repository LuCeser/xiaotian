# Phase 8.1 Research: Multi-Word Dictation Flow

**Researched:** 2026-08-10
**Domain:** Go session FSM extension + WebSocket control-frame emission + vanilla-JS frontend wiring
**Confidence:** HIGH (design is settled via D-01..D-06; all code sites read this session and quoted verbatim)

## Summary

This phase is a **small, surgical extension**, not new architecture. The design is locked
(`08.1-CONTEXT.md` D-01..D-06, confirmed "全部采纳"). Mechanically it is four edits against
existing code: (1) one new case in `transition()` for `DICTATING + EventWordComplete` (D-02);
(2) one word-0 auto-start trigger in `handleStartSession` after `session_ready` (D-01/D-03);
(3) emit `progress_update{word_id}` on entering LISTENING and `session_complete{totalWords}`
on entering WAITING_PARENT, both inside `onTransition` (D-04/D-06); (4) one `setState` line in
the frontend `_applyProgressUpdate` to set `currentWordId` (D-04). D-05 adds no code — it is a
"do not prefetch yet" decision.

The two things the planner must get exactly right are: **(a) the D-03 trigger-site choice**
(Option A — push an internal `play_word` from `handleStartSession` *after* `session_ready` — is
strongly recommended; Option B has a wire-ordering bug); and **(b) the word_id-before-audio
ordering invariant**, which holds iff `progress_update` is emitted *synchronously in
`onTransition` before* `spawnStreamWord()` is called (the FIFO client send-channel then
guarantees wire order).

**Primary recommendation:** Implement Option A for D-03; extend `onTransition` to emit
`progress_update` then call `spawnStreamWord`, and emit `session_complete` on WAITING_PARENT;
mirror the existing `fsm_test.go` table-driven style for the new FSM case; add one real-WS
integration test (the `handlers_test.go` pattern) asserting the full frame sequence.

## D-03 Trigger-Site Analysis (the one open planner decision)

The two options, grounded in the current code read this session. **Recommendation: Option A.**

### Option A — Push an internal `play_word` event from `handleStartSession` after `session_ready` (RECOMMENDED)

**Exact code location:** `cmd/service/handlers.go:173-205` (`handleStartSession`). Today it
calls `manager.NewSession` (line 181), sends `session_ready` via `sendControlFrame` (lines
197-202), and returns (line 204).

**Precise change:** after the `session_ready` send succeeds, add one push onto the session's
event channel:

```go
// after the session_ready sendControlFrame block (handlers.go ~line 202):
manager.Push(clientConnID(client), session.SessionEvent{
    Type:        session.EventControlFrame,
    ControlType: "play_word",
})
```

**Why this works:**
1. **Reuses the existing `IDLE + play_word → LISTENING` transition** (`fsm.go:41-49`,
   verbatim: `case EventControlFrame: if ev.ControlType == "play_word" { s.wordIndex = 0;
   s.state = database.StateListening; return nil }`). No FSM change is needed for word-0 start;
   D-02's FSM change is only for *between-word* advance. Only the *trigger* changes from
   client-sent to backend-internal.
2. **Single-writer invariant (Phase 7 D-02) preserved.** `manager.Push` is a channel send
   (`manager.go:204-209` → `session.go:305-310`), not a state mutation. The event-loop goroutine
   remains the sole writer; it processes the event through `transition()`.
3. **Wire ordering is correct by construction.** `handleStartSession` runs `sendControlFrame(
   session_ready)` synchronously (it returns after `client.Send` queues the frame), *then* pushes
   `play_word`. The event loop can only process `play_word` after the push, so `progress_update`
   (emitted in `onTransition`) is queued into the same FIFO client send-channel *after*
   `session_ready`. Resulting wire order: `session_ready → progress_update(word0) → audio…`.
4. **`Manager.NewSession` is the WRONG sub-site.** `manager.go:191` runs `go s.run(s.runCtx)`
   *before* `handleStartSession` sends `session_ready`. If `NewSession` pushed `play_word`
   itself, the event loop could emit `progress_update`/audio *before* `session_ready` is sent —
   an ordering bug. Keep the push in the handler, after `session_ready`.

**Blast radius:** ~3 lines in one function. No new event type, no FSM change, no manager change.

### Option B — Auto-transition `IDLE → LISTENING` at `Start()` / top of `run()`

**Exact code location:** `pkg/session/session.go:224-228` (`Start`) or the top of `run()`
(`session.go:243`, before the `for`/`select` loop at line 280).

**Precise change:** at the top of `run()`, before the loop, call
`s.transition(SessionEvent{Type: EventControlFrame, ControlType: "play_word"})` then
`s.onTransition()` — reusing the same `IDLE + play_word → LISTENING` case.

**Why it is inferior:**
1. **Wire-ordering bug.** `Manager.NewSession` starts the session goroutine (`manager.go:191`)
   *before* `handleStartSession` sends `session_ready` (`handlers.go:197`). If `run()` auto-starts
   word 0 immediately on entry, `progress_update(word0)` + audio frames race ahead of
   `session_ready` on the wire. The frontend's `_applyProgressUpdate` would run before
   `_applySessionReady` set `totalWords`, and `app.js` audio routing would receive frames before
   the UI entered `DICTATING`. Fixing this requires reordering the Start/session_ready lifecycle
   — a larger, riskier change than Option A.
2. **Bypasses the channel mechanism** with a "magic" auto-trigger inside `run()`. It still
   preserves the single-writer invariant (it runs in the event-loop goroutine), but it is less
   consistent with the "everything is an event on the channel" pattern (Phase 7 D-02 mirrors
   `ws.Hub.Run`'s channel-select).
3. Larger blast radius (touches `session.go` lifecycle) for no benefit over Option A.

**Recommendation:** **Option A.** It is the cleanest trigger site: minimal, reuses the existing
transition + channel, and — critically — preserves the `session_ready → progress_update → audio`
wire ordering without lifecycle reordering. Option B's ordering bug is the dealbreaker.

> Planner note: whichever option is chosen, the `session_ready → (progress_update → audio →
> word_complete)×N → session_complete` ordering invariant must be asserted by the integration
> test (§"Test Strategy").

## FSM Transition Extension (D-02)

### Current `transition()` shape for `StateDictating`

From `pkg/session/fsm.go:66-80` (read this session, quoted verbatim):

```go
case database.StateDictating:
    switch ev.Type {
    case EventControlFrame:
        if ev.ControlType == "next_word" {
            if s.wordIndex >= len(s.wordQueue)-1 {
                // Last word exhausted → wait for parent review (D-12: no
                // UpdateRatings call).
                s.state = database.StateWaitingParent
                return nil
            }
            s.wordIndex++
            s.state = database.StateListening
            return nil
        }
    }
```

### The new case to add (D-02)

Add a second arm inside `case database.StateDictating:` for `EventWordComplete`. It mirrors the
existing `next_word` branch exactly (same last-word check, same `wordIndex++`), because the
intent is identical — advance to the next word — only the *signal* differs (system-driven
`WordComplete` instead of client `next_word`):

```go
case database.StateDictating:
    switch ev.Type {
    case EventControlFrame:
        if ev.ControlType == "next_word" {
            // ... existing next_word branch unchanged ...
        }
    case EventWordComplete:
        // D-02 (Phase 8.1): system-driven auto-advance. StreamWord completion
        // for the current word drives the next word with no client round-trip.
        if s.wordIndex >= len(s.wordQueue)-1 {
            s.state = database.StateWaitingParent
            return nil
        }
        s.wordIndex++
        s.state = database.StateListening
        return nil
    }
```

**Purity confirmed.** `transition()` already takes `s.mu.Lock()` (line 37) and mutates only
`s.state` and `s.wordIndex` — no I/O, no frame emission, no goroutine spawn. The new case keeps
this contract. All side effects (streaming, emission) happen in `onTransition`, which the event
loop calls after a successful transition (`session.go:337`).

**`EventWordComplete` constant:** `EventType = 0x02` (`types.go:44`, verbatim:
`EventWordComplete EventType = 0x02`). No new event type is introduced — the same
`EventWordComplete` that today drives `LISTENING → DICTATING` (`fsm.go:51-58`) now *also* drives
`DICTATING → LISTENING | WAITING_PARENT`. The event is already pushed by `spawnStreamWord`
(`session.go:389`: `case s.events <- SessionEvent{Type: EventWordComplete, WordID: wordID}:`).

## Emission Sites & Ordering Invariant (D-04, D-06)

### Where `onTransition` hooks live today

From `pkg/session/session.go:343-357` (read this session, quoted verbatim):

```go
func (s *Session) onTransition() {
    s.mu.Lock()
    s.deadline = time.Now().Add(s.timeoutFor(s.state))
    newState := s.state
    s.mu.Unlock()

    s.auditState(newState)

    // D-13: on entering LISTENING, the Session owns the StreamWord call. On its
    // return, a goroutine pushes WordComplete onto the events channel, driving
    // the LISTENING→DICTATING system transition.
    if newState == database.StateListening {
        s.spawnStreamWord()
    }
}
```

`onTransition` is called from the event-loop goroutine after every successful transition
(`session.go:337`: `s.onTransition()`). It is the canonical place for state-entry side effects.

### The extension (D-04 + D-06)

Extend `onTransition` so that:
- **On entering LISTENING:** emit `progress_update` (carrying `word_id`) **before** calling
  `spawnStreamWord()`.
- **On entering WAITING_PARENT:** emit `session_complete`.

```go
func (s *Session) onTransition() {
    s.mu.Lock()
    s.deadline = time.Now().Add(s.timeoutFor(s.state))
    newState := s.state
    wordIndex := s.wordIndex          // capture under lock
    s.mu.Unlock()

    s.auditState(newState)

    switch newState {
    case database.StateListening:
        // D-04: emit progress_update BEFORE streaming so the frontend sets
        // currentWordId before this word's audio frames arrive.
        s.emitProgressUpdate(wordIndex)   // NEW — must precede spawnStreamWord
        s.spawnStreamWord()
    case database.StateWaitingParent:
        // D-06: last word done → session_complete. No new terminal state.
        s.emitSessionComplete()           // NEW
    }
}
```

### How `word_id`-before-audio ordering is guaranteed

The invariant — `progress_update{word_id}` MUST reach the client before that word's audio frames
— holds **iff `emitProgressUpdate` runs synchronously in `onTransition` before `spawnStreamWord`
is called**. Proof, grounded in the code:

1. `emitProgressUpdate` calls `s.client.Send(frame)` synchronously, which queues the frame into
   the client's FIFO send channel (per `handlers_test.go:19-24`: "*`Send()` drops into an
   internal buffered channel drained by the unexported `writePump`*"). Channel writes are
   goroutine-safe and FIFO.
2. `spawnStreamWord` (`session.go:362-393`) then spawns a goroutine (line 375: `go func() { …
   s.streamer.StreamWord(…) … }`). That goroutine's first audio-frame `client.Send` can only
   happen *after* the goroutine is scheduled *and* `StreamWord` has loaded PCM and encoded its
   first frame — strictly later than the synchronous `progress_update` send that already
   preceded `spawnStreamWord`.
3. Both frames enter the **same** FIFO send channel on `s.client`, so the wire order matches the
   queue order: `progress_update` first, then audio frames. ✓

**Do not** emit `progress_update` from inside `spawnStreamWord`'s goroutine or after it — that
would race the audio frames on the channel and could invert the order.

### The emission helper (mechanics)

`sendControlFrame` (`handlers.go:362-378`) lives in package `main` and is not reachable from
`pkg/session`. The session package already imports `pkg/ws` (`session.go:19`) and holds
`s.client *ws.Client`. Add a small private helper in `pkg/session` that mirrors the handler
helper, using `ws.EncodeFrame` (`pkg/ws/codec.go:47`, signature `func EncodeFrame(h
*FrameHeader, payload []byte) []byte`):

```go
// emitControl builds a JSON control frame and sends it via s.client. Nil-safe
// (tests pass nil client). Mirrors cmd/service sendControlFrame.
func (s *Session) emitControl(msgType ws.MessageType, payload interface{}) {
    if s.client == nil {
        return
    }
    b, err := json.Marshal(payload)
    if err != nil { s.logger.Warn(...); return }
    frame := ws.EncodeFrame(&ws.FrameHeader{
        Version: ws.ProtocolVersion, MsgType: msgType,
        Sequence: 0, PayloadLen: uint16(len(b)),
    }, b)
    if err := s.client.Send(frame); err != nil { s.logger.Warn(...) }
}
```

**MsgType choice:** use `ws.MsgTypeControl` (`protocol.go:31`, value `0x02`) for both
`progress_update` and `session_complete`, matching `session_ready` (sent via
`sendControlFrame`→`MsgTypeControl`). The frontend dispatches *all* non-audio frames by their
JSON `type` field regardless of MsgType (`websocket-client.js:201-225`: AUDIO is routed
separately; everything else is text-decoded → JSON-parsed → `handleControlFrame`), so MsgType is
not load-bearing on the frontend — but consistency with `session_ready` is the right call.

> **Note on `word_complete`'s MsgType:** `word_complete` is emitted by the *streamer*
> (`streamer.go:174-182`) as `ws.MsgTypeStatus` (`0x06`), not Control. This is pre-existing and
> unchanged. The frontend handles it fine (non-audio → JSON dispatch). Do not "fix" this — it is
> out of scope and would touch the locked frame protocol.

### Nil-safety

`s.client` is `*ws.Client` and is `nil` in many existing tests (`session_test.go` passes `nil`
for client in `TestNewSession_SelectDueCards` etc.). The emission helper MUST nil-guard
(mirroring `spawnStreamWord`'s `if s.streamer == nil { return }` guard at `session.go:363` and
`unregisterFromHub`'s `if s.hub == nil || s.client == nil { return }` at `session.go:457`).

## word_id Source & Frontend Wiring (D-04)

### The routing key is the word STRING

`spawnStreamWord` computes the routing key today (`session.go:371`, verbatim):
`wordID := s.wordQueue[s.wordQueue[s.wordIndex].Word`. Wait — corrected verbatim quote:
`wordID := s.wordQueue[s.wordIndex].Word` (line 371). This `wordID` is passed to
`streamer.StreamWord(ctx, s.client, s.id, wordID, 0)` (line 377), and `sendWordComplete`
(`streamer.go:160-165`) emits `{"type":"word_complete","word_id": wordID}` — i.e. the **word
string**.

`DueCard.Word` is `string` with tag `json:"word"` (`pkg/pybridge/executor.go:99`, verbatim:
`Word string \`json:"word"\``). There is no separate stable numeric id used as the audio routing
key — `DueCard.ID` (`int`, line 98) is the FSRS card id, never sent on the wire for audio.

**Therefore `progress_update.word_id` MUST be `wordQueue[wordIndex].Word`** (the same string
`spawnStreamWord` uses). This keeps all three frame families — `progress_update.word_id`,
audio-frame routing (via `state.currentWordId`), and `word_complete.word_id` — keyed identically
so the frontend's `pendingPcm.get(wordId)` lookup in `playWordComplete` (`audio-controller.js:
178`) resolves.

### The exact `progress_update` payload

The frontend's `_applyProgressUpdate` (`websocket-client.js:467-489`) validates `currentWord`
and `completedWords` as non-negative numbers (lines 468, 473) and rejects
`completedWords > totalWords` (line 481). The `word_id` field is a new additive string — it does
not trip any existing validation. State-manager semantics (`state-manager.js:58`): `currentWord`
is **1-based**; `completedWords` is the count fully delivered so far.

Recommended backend payload, computed in `emitProgressUpdate(wordIndex)`:

| Field | Value | Why |
|-------|-------|-----|
| `type` | `"progress_update"` | matches `handleControlFrame` dispatch (`websocket-client.js:417`) |
| `currentWord` | `wordIndex + 1` | 1-based (state-manager.js:58) |
| `completedWords` | `wordIndex` | words completed *before* this word (word 0 → 0; word 1 → 1; …) — consistent with `_applyWordComplete`'s increment (`websocket-client.js:501`) so no double-count |
| `word_id` | `s.wordQueue[wordIndex].Word` | the audio routing key (see above) |

`emitSessionComplete()` payload: `{"type":"session_complete","totalWords": len(s.wordQueue)}`.
`_applySessionComplete` (`websocket-client.js:515-522`) reads `payload.totalWords` and sets
`completedWords: total` + `status: 'FEEDBACK'`.

### The single frontend wiring line (D-04)

`_applyProgressUpdate` today (`websocket-client.js:485-488`, verbatim):
```js
this.stateManager.setState({
    currentWord: payload.currentWord,
    completedWords: payload.completedWords
});
```
Extend to:
```js
this.stateManager.setState({
    currentWord: payload.currentWord,
    completedWords: payload.completedWords,
    currentWordId: typeof payload.word_id === 'string' ? payload.word_id : this.stateManager.getCurrentWordId()
});
```
- `getCurrentWordId()` (`state-manager.js:224-226`) returns `this.state.currentWordId || null`.
- `currentWordId` is initialized to `null` (`state-manager.js:62`, verbatim:
  `currentWordId: null, // word whose audio frames are currently being accumulated`).
- `_validateStateUpdate` (`state-manager.js:246-269`) does **not** validate `currentWordId`, so
  adding it to `setState` will not be rejected.
- The `|| getCurrentWordId()` fallback preserves backwards-compatibility if a `progress_update`
  ever arrives without `word_id` (keeps the prior value).

This unblocks the audio frame-drop: `app.js handleMessage` (`app.js:226-244`) reads
`var wordId = state.currentWordId || null` (line 235) and passes it to
`audioController.handleAudioFrame(payload, sequence, wordId)`; `handleAudioFrame`
(`audio-controller.js:139-166`) drops the frame when `wordId` is falsy (lines 157-159, verbatim:
`if (!wordId) { console.warn('[audio] Frame received with no wordId — ignored …'); return; }`).

## Test Strategy

### Unit — FSM transition table (mirror `fsm_test.go`)

- **File:** extend `pkg/session/fsm_test.go`.
- **Pattern:** table-driven `TestTransition` (`fsm_test.go:13-93`) + a focused
  `TestTransition_WordComplete_LastWord` mirroring `TestTransition_LastWord` (`fsm_test.go:
  97-108`). Construct `&Session{state, wordQueue, wordIndex}` directly — no event loop, no
  client. See §"FSM Transition Extension" for the exact cases.
- **Coverage:** `DICTATING + WordComplete` → LISTENING (more words); → WAITING_PARENT (last
  word); wordIndex increment correctness; purity (no mutation on the still-valid
  `LISTENING + WordComplete → DICTATING` path).

### Integration — full frame sequence (the Nyquist-critical test)

- **Assertion:** for a 3-word session, the wire sequence is exactly
  `session_ready → (progress_update{word_id} → audio* → word_complete{word_id})×3 →
  session_complete{totalWords}`, AND each `progress_update.word_id` precedes that word's first
  audio frame, AND `progress_update.word_id == word_complete.word_id` per word.

**Test seam decision (planner picks; recommendation first):**

- **(Recommended) Real-WS integration test, the `handlers_test.go` pattern.**
  `cmd/service/handlers_test.go:29-133` already proves the technique: spin up `httptest.Server`
  + `ws.NewServer` + a real `gorilla/websocket` dialer, capture the server-side `*ws.Client`,
  decode frames received client-side via `ws.DecodeFrame`. Drive `handleStartSession` (or push
  `play_word`), then read & decode frames from the dialer, asserting type + order. This is the
  highest-fidelity seam because `s.client` is concrete `*ws.Client` (not an interface), so an
  in-process fake cannot intercept `s.client.Send` without a refactor.

- **(Alternative) Introduce a narrow emission interface.** Add e.g.
  `ControlFrameEmitter interface { SendControlFrame(msgType, payload) }` to `pkg/session`,
  satisfied structurally by a thin adapter over `*ws.Client`, and inject it via `NewSession`

## Gapless Timing Sanity (D-05)

### Correction to the CONTEXT/DESIGN-ANALYSIS prefetch claim

`08.1-CONTEXT.md` states "SessionCache already prefetches the first 10 words". This is
**inaccurate**. Verified this session:

- `GenerateForSession` (`pkg/tts/generator.go:60-138`) writes PCM to **disk** via
  `g.cache.Store(sessionID, wordID, pcmData.Samples)` (line 124) for every word. It does **not**
  populate the streamer's in-memory `prefetch` map.
- `Streamer.PrefetchNext` (`streamer.go:197-220`) is the only thing that populates the
  in-memory `prefetch` map. A repo-wide search (`grep '\.PrefetchNext\('`) finds it called
  **only in tests** (`streamer_test.go:453,499,537,769`) — **never in production code**.
- So at runtime, `StreamWord` (`streamer.go:61-81`) finds the `prefetch` map empty and falls
  back to `s.cache.Load(sessionID, wordID)` — a **disk read** (local SSD on dev / VPS disk in
  prod).

**D-05's conclusion still holds**, just via a different mechanism: the inter-word delay is a
disk read + goroutine spawn + frame slicing/encoding — sub-second — vs typical word durations
>1s. So the 07.1 audio-clock gapless bar (D-04 `scheduledTime += buf.duration`,
`audio-controller.js:226-227`) is met as long as word_{i+1}'s `word_complete` fires (and
`playWordComplete` schedules it on the clock) before word_i's audio finishes playing on the
hardware clock. Because `word_complete` for word_{i+1} only fires *after* all its PCM has been
sent, the frontend always has the full buffer before scheduling — the only risk is the gap
between word_i's hardware-clock end and word_{i+1}'s scheduling moment, which the underrun-snap
at `audio-controller.js:222-224` (`if (this.scheduledTime < this.audioCtx.currentTime)
{ this.scheduledTime = this.audioCtx.currentTime; }`) absorbs.

**Implication for the deferred prefetch:** wiring `PrefetchNext` (it already exists,
`streamer.go:197`) becomes the natural lever if real-iPad profiling shows an audible gap — call
it for the next 1–2 words from `onTransition` on entering LISTENING. This is explicitly deferred
(D-05); flagged here only so the planner knows the lever exists and is cheap.

### Real-iPad profiling concern

The acceptance bar is Phase 07.1 D-13 (real iPad, gapless 20–30 words). The VPS disk-read path
is the one unknown: if the 1C/1G VPS disk is slow under load, the first inter-word gap *could*
be audible. This is a **profile-on-real-hardware** risk, not a design risk — the auto-advance
architecture is correct; only the disk-latency assumption needs empirical confirmation. No code
change is proposed for v1 (D-05).

## Risks & Open Questions

1. **D-03 trigger-site (OPEN — planner decides).** Option A recommended (§"D-03 Trigger-Site
   Analysis"). Option B has a wire-ordering bug unless the Start/session_ready lifecycle is
   reordered. The planner must pick; this research gives a grounded recommendation but the
   decision is the planner's per `08.1-CONTEXT.md` Discretion.

2. **Emission test seam (planner decides).** Real-WS integration test (recommended) vs narrow
   `ControlFrameEmitter` interface. Affects test ergonomics only, not production shape. See
   §"Test Strategy".

3. **`progress_update`/`session_complete` Sequence field.** Audio frames are monotonic per
   session (`streamer.go:237-243`, `seqCounters`), and control frames from the handler use
   `nextControlSeq()` (`handlers.go:33`). The new session-emitted control frames go through a
   *different* path (`s.client.Send` directly, not `handlers.go sendControlFrame`). The planner
   should decide whether `progress_update`/`session_complete` need monotonic Sequence values
   too. The frontend does **not** dedup control frames by Sequence (it dedups *audio* frames by
   sequence in `audio-controller.js:147-153`); control frames are dispatched purely by JSON
   `type`. So Sequence on these control frames is currently **not load-bearing** on the
   frontend — `Sequence: 0` is acceptable (matching `word_complete`'s `Sequence: 0` at
   `streamer.go:178`). Recommend `0` for simplicity unless a future need arises.

4. **`progress_update` for word 0 vs `session_ready`.** Both set progress-related fields.
   `session_ready` (`_applySessionReady`, `websocket-client.js:437-452`) sets `currentWord:0,
   completedWords:0` (0-based start). Then `progress_update(word0)` sets `currentWord:1,
   completedWords:0, currentWordId`. No conflict — `progress_update` refines the initial state.
   The planner should confirm the backend emits `progress_update(word0)` (it will, via
   `onTransition` on the first LISTENING entry driven by Option A's `play_word` push).

5. **No JS tests.** The `_applyProgressUpdate` one-liner is verified only by the real-iPad
   manual flow. Low risk (additive field, fallback-guarded), but the planner should note in
   VALIDATION that D-04's frontend half is manual-only.

6. **`word_complete` from a stale goroutine.** `spawnStreamWord` cancels any in-flight stream
   before starting a new one (`session.go:367-369`). In the auto-advance flow there is no
   replay, so this is not triggered — but the planner should preserve the existing cancel logic
   untouched (it is correct and out of scope).
