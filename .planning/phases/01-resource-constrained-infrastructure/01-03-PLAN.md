    - Return error if level parsing fails.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request → handler | Untrusted request body enters; panic represents malformed or malicious input triggering a bug |
| Handler → Logger | Handler-supplied field values cross into log stream; sanitization is the gate |
| Logger → log sink (stderr/file) | Output crosses to aggregation system; structured JSON defends parser integrity |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09 | Tampering | Log injection via malicious input | high | mitigate | sanitizeString() in ZapLogger strips \\n, \\r, \\t before emission; TestFieldSanitization proves it. Field values use zap.Any typed encoding, not string interpolation. |
| T-01-10 | Information Disclosure | Panic value leaked to client | high | mitigate | RecoveryMiddleware writes a generic "internal server error" body, never the panic value or stack. Stack trace goes only to logs. |
| T-01-11 | Denial of Service | Verbose logging exhausts disk | medium | mitigate | LogConfig.Level is configurable; production default is "info" (not debug). D-26 service-level metrics (not per-component) reduce volume. |
| T-01-12 | Repudiation | Missing request correlation | medium | mitigate | Logger.With(...) supports request_id propagation; RecoveryMiddleware TestRecoveryMiddlewareIncludesRequestID verifies inheritance. |
| T-01-13 | Information Disclosure | Stack traces in production logs | low | accept | Stack traces are required for debugging; log sinks are operator-controlled. Mitigation via access controls on log aggregation is out of Phase 1 scope. |
</threat_model>
