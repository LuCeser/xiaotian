## Gap Context (G-08-3)

**From 08-VERIFICATION.md Truth #15, #17, #18:**
- Truth #15: "Progress bar updates in real-time as backend sends progress updates" → PRESENT_BEHAVIOR_UNVERIFIED
- Truth #17: "Completed words count updates as student progresses through session" → PRESENT_BEHAVIOR_UNVERIFIED  
- Truth #18: "Progress bar visual representation fills from 0% to 100%" → PRESENT_BEHAVIOR_UNVERIFIED

**Root Cause:**
Frontend handleControlFrame dispatcher (websocket-client.js:405-447) correctly handles progress_update, word_complete, and session_complete frame types. AudioController (audio-controller.js:279-290) expects word_complete to trigger playWordComplete(). BUT backend handlers.go has NO emission sites for these frame types - grep confirms only session_ready + error are emitted.

**Frontend Gap:**
Frontend never sends play_word control frame to trigger backend StreamWord. Without this trigger, the backend never starts streaming audio frames, and therefore never emits completion signals.

**Why This Gap Exists:**
Phase 08 SUMMARYs explicitly deferred backend progress frame emission as "future backend work (multi-word sequential streaming)" without assigning an owner phase. This created a cross-phase dependency where the frontend contract was defined and implemented, but the backend data source was never built.

**Impact on Phase 08 Goal:**
Roadmap SC 2 ("Interface displays real-time session progress") cannot be exercised without these backend emissions. The frontend ProgressDisplay component is fully implemented but receives no data to display.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→backend WebSocket | Control frames (play_word, progress_update, etc.) flow over WebSocket connection |
| backend session FSM | Internal state machine emits progress frames based on dictation progress |

## New Control Frame Threat Analysis

Adding new control frame types introduces new WebSocket message types that must be validated:

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-06 | Injection | WebSocket control frames | medium | mitigate | Apply T-08-05 validation (already present) to new frame types: validate all required fields present, check types, reject malformed frames. |
| T-08-07 | DoS | Progress frame flood | low | accept | Backend controls emission rate (bounded by word streaming speed). Frontend handleControlFrame is non-blocking. |
| T-08-08 | Information Disclosure | Session state exposure | low | accept | Progress frames reveal dictation progress to client. This is intended behavior for the student interface. |

**Existing mitigations from Phase 08:**
- Frontend handleControlFrame has T-08-05 validation for session_ready frames (validates session_id + words presence)
- Same validation pattern should be applied to progress_update, word_complete, session_complete
- WebSocket message size limit (1MB) prevents large payload attacks

**Gap closure focus:** Apply existing validation patterns to new frame types. No new security boundaries introduced.
</threat_model>
