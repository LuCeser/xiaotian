<objective>
Fix static file serving 404 errors by ensuring service runs from correct working directory so config.yaml is found and static file server is properly mounted.

Purpose: The code is working correctly - StaticFileServer serves files properly when configured. The issue is operational: service starts from temp Go build directory, relative config.yaml path fails resolution, LoadConfig() silently falls back to DefaultConfig() with empty StaticDir, disabling static file serving. This causes service to serve debug test-interface.html instead of student interface.

Output: Service running from repo root with config.yaml loaded, static file server mounted at "/" serving pkg/web/static/index.html with all CSS/JS subresources returning 200 OK.
</objective>

## Gap Context (G-08-2)

**From UAT.md Test 2 (Static File Serving):**
- Expected: Navigate to server URL, student interface loads with proper MIME types
- Actual: HTML page loads correctly (text/html; charset=utf-8), but JS/CSS files return 404
- Severity: major
- Status: failed

**From debug/static-file-404.md Root Cause:**
Service runs from temp Go build directory (C:\Users\fortu\AppData\Local\Temp\go-build2890987147\b001\exe\service.exe) instead of repo root. Relative config.yaml path fails to resolve, LoadConfig() silently falls back to DefaultConfig() with StaticDir: "" (empty), which disables static file serving. Service then serves test-interface.html instead of pkg/web/static/index.html.

**Key Evidence Chain:**
1. Process running from temp directory → config.yaml not found at relative path
2. LoadConfig() (config.go:714-729) silently skips missing config, falls back to DefaultConfig()
3. DefaultConfig() (config.go:619) has StaticDir: "" → static serving disabled
4. main.go (lines 394-396) mounts debug handler when StaticDir is empty
5. Debug handler serves test-interface.html, which doesn't have CSS/JS files → 404s

**Why Code Is Correct:**
The code logic is working as designed. LoadConfig() is intentionally lenient (allows cross-CWD boot). StaticDir defaults to empty (opt-in behavior) following Database.Path precedent. The problem is purely operational: service startup procedure doesn't ensure correct working directory.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→static server | Browser requests static files, no authentication required |
| deployment→service | Admin starts service, must ensure correct working directory |

## Working Directory Impact Analysis

Changing service working directory affects ALL relative path resolution in the service, not just static file serving:

| Component | Relative Path Used | Impact of Wrong CWD |
|-----------|-------------------|-------------------|
| config.yaml discovery | -config config.yaml (relative path) | LoadConfig fails → DefaultConfig with empty StaticDir |
| StaticFileServer | ServerConfig.StaticDir = "./pkg/web/static" | Static files 404, debug test-interface.html served |
| Database path | Database.Path in config (often relative like "./data/xiaotian.db") | May create database in wrong location or fail to find existing |
| Log files | Logging config with relative paths | Logs written to wrong directory |
| Audio buffer pool | Temporary file paths | May fail or create temp files in wrong location |
| TTS cache | Cache directory paths | May not find cached audio files |

**Key insight:** The fix (running from repo root) ensures ALL relative paths resolve correctly, not just static file serving.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-05 | Tampering | config.yaml | low | accept | Config files are operator-controlled, not user input. Document verification of config loaded via logs. |
| T-08-06 | Information Disclosure | Static file serving | medium | mitigate | Already mitigated by StaticFileServer path-traversal protection in pkg/infra/static.go (http.Dir containment). Verify this is still active after fix. |
| T-08-07 | Denial of Service | Service startup failure | low | accept | If wrong working directory, service starts but static files 404. Service doesn't crash, just serves wrong content. Operational issue, not security. |
| T-08-08 | Information Disclosure | Database files | low | accept | Wrong CWD could create database in temp directory with wrong permissions, but this is an operational error not an attack vector. Mitigated by documentation. |
| T-08-09 | Denial of Service | Log file creation | low | accept | Service may fail to create logs in temp directory. Operational issue, mitigated by correct startup procedure. |

**Gap closure focus:** No new security threats introduced. This is an operational fix that ensures ALL relative paths resolve correctly. Existing mitigations in StaticFileServer (path traversal) remain in place. Documentation of working directory requirement prevents future operational mistakes.
