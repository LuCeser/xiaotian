## Summary

本阶段交付五件套：两阶段 save-receipt store（`lesson_save_receipts`）挂载到四个提交端点、两条只读家长路由（`GET /api/v1/lessons`、`GET /api/v1/lessons/{id}`）、家长页三 tab + LessonsView、`rt.forceStudentMode` 强制学生投影开关、静态 `home.html` 两扇门页与 tutor 页终态「回首页」链接。

对两条最高价值红线做了重点对抗性核查，均**未发现可证明的违背**：

1. **白名单泄漏线（13.3-02）**：`lessonListItem` 类型结构上不含任何词面字段；in-progress lesson 在 detail 端点走 `writeJSON(w, item)` 序列化层短路，词面键在 JSON 里不存在（非"值为空"）；完成判定 `LessonCompleted` 与 `pkg/rt/turn.go` 会话初始化分支表逐支对齐（checking 恒不完成、legacy 空卡不完成）；httptest 层有 `assertSummaryKeysExact` 的精确键集断言 + 序列化 DOM 负向扫描，mock e2e 层另有 `zephyr/onyx/marina` 三词负向 canary。receipt 词集（requested/updated/missing）只对 completed lesson 输出，而 completed 意味着 D-10 已 unmask，不构成泄漏。层层核查后未找到泄漏通道。
2. **receipt bypass 纪律（13.3-01）**：四处挂载（`finishCheckSubmit` / `finishCorrections` / `uncheckedCloseFallback` / `finishPracticeSubmit`）全部是纯旁路——Begin/Complete 失败只发 `EventError(at=save_receipt)`，从不提前 return、不触碰 `saveFailed`/`updated`/`missing`、不驱动重写；`TestSaveReceiptFailureIsBypass` 钉死了 review_result 字节级不变 + SubmitReview 恰好 1 次。unchecked_fallback 的挂载点位于 `res.Idempotent` 守卫之后，replay 路径零回执，无重复行风险。

`go build ./...`、`go vet` 与 `pkg/lesson`、`pkg/web/api`、`pkg/infra`、`pkg/rt` 四包测试（`-count=1`）全部通过。审查中发现并**主动撤回了一个假阳性**：曾怀疑学生播报「对了 X 个」（`check.go` 全量 verdicts 计数）与家长端 manual-only 口径（`store.go SummarizeLesson`）矛盾，深挖后发现提交门（`handleCheckSubmit` 的 manual gate）保证提交时刻所有 verdict 均为 manual=true，而唯一保留 manual=false verdict 的 unchecked-fallback 路径不播 summary，因此两个口径在所有可观察场景下数值一致，不构成缺陷。

遗留 1 项 Warning（receipt 聚合失败毒化整个学习记录页）与 5 项 Info，详见下文。

## Warnings

### WR-01: 一条损坏的 receipt 行会让整个学习记录页 500（辅助字段毒化主页面）

**File:** `pkg/web/api/handlers.go:610-619`（listLessons）、`pkg/web/api/handlers.go:663-673`（getLesson）
**Issue:** `listLessons` 在 `receipts.LatestByLessonIDs` 出错时对**整个列表**返回 500；`getLesson` 同样在 receipt 查询出错时直接 500。而 `ReceiptStore.LatestByLessonIDs`/`ListByLesson` 的契约（`pkg/lesson/receipt_store.go:225-227, 252-275`）是"损坏的非空 JSON 显式报错"（decode 失败即 error）。两条契约组合的后果：数据库中**任何一行** receipt 的词集列被手改/部分写入损坏（哪怕属于一个月前的旧课），家长学习记录 tab 的列表与详情都会整体不可用（空列表 + 错误横幅）。save_status 只是 11 个 summary 字段中的 1 个辅助字段，却拥有一票否决整页的能力，违反比例原则；也和该阶段自己确立的降级语义（`save_status=unknown`＝「保存状态未知」）不匹配——对损坏行显示 unknown + 服务端错误日志，比让家长核心新功能全灭更诚实也更有用。
**Fix:** 聚合查询失败时降级而非失败：捕获 error 后记日志，让对应行（或全部行）按 `save_status=unknown` 渲染。例如在 `listLessons` 中：

```go
latest, err := h.receipts.LatestByLessonIDs(r.Context(), ids)
if err != nil {
    h.logger.Error("list lessons: receipt aggregation failed",
        infra.F("component", "web/api"),
        infra.ErrField(err),
    )
    latest = map[string]lesson.Receipt{} // degrade: rows render save_status=unknown
}
```

`getLesson` 的两处 receipt 查询同理（detail 的 `save_receipts` 数组降级为空数组 + 日志）。若希望保留对"系统性 DB 故障"的严格失败，可只对 decode 类错误降级、连接类错误照旧 500，但需要区分错误类别，成本更高；统一降级到 unknown 已足够诚实。

## Info

### IN-01: 家长端日期显示用 UTC 日期，北京时间 00:00–08:00 的课会标成前一天

**File:** `pkg/web/static/js/parent-lessons.js:115-121`
**Issue:** `formatDay` 直接截取 `created_at`（SQLite `datetime('now')`＝UTC）的日期部分，注释声明这是故意的（避免客户端时区换算误标）。但对北京时间早上 8 点前的默写课，家长看到的日期会比实际（北京日历）早一天，与 lesson id 的 `r0-YYYYMMDD`（北京日历）直观不一致——同一条记录，id 里的日期和列表显示的日期可能不同。
**Fix:** 最低成本方案：列表与详情头部的日期由后端投影时转成北京日历日（与 `beijingDay` 同一 `FixedZone` 纪律）再输出一个显示用字段；或前端按 UTC+8 固定偏移换算（该产品用户群固定在 UTC+8，`resolvePracticeLessonID` 已用同一约定）。若维持现状，建议至少在 UI 上注明"记录日期为 UTC"。

### IN-02: mock stub 的 practice detail `words: []` 与真实后端行为相反，mock-parity 声明失真

**File:** `tests/e2e-rt/mock-rt-server.js:271-289`
**Issue:** stub 注释称 "Practice lessons carry no word cards, so `words` is empty"，但真实链路是 `handlePracticeInit` → `EnsureLessonCards`（cards 含 word/meaning/example）→ 完成后 `getLesson` 的 `detail.words` **非空且带释义**。mock e2e 因此永远验证不到"加练详情渲染逐词释义"的真实路径；"field-for-field mock parity"的声明在这一点上与真实行为相反。现有断言未依赖该差异所以不挂，但后续依赖 mock 写的前端测试会在真实后端上暴露差异。
**Fix:** 将 stub ④ 的 `words` 改为与真实一致的 `[ {word:'guitar', meaning:..., example:...}, ... ]`（lesson ② 的形状），并补一条"practice 行渲染释义"的断言。

### IN-03: config.example.yaml 的 rt 段缺少 allowedOrigins 的生产提示（对比 ws 段）

**File:** `config.example.yaml:196-223`
**Issue:** `ws:` 段有大段"PRODUCTION MUST set the real origin(s)"与 IN-03 端口匹配说明，而 `rt:` 段只有 `forceStudentMode` 的注释。`RTConfig` 的默认 origins 是 `["localhost","127.0.0.1"]`（`pkg/infra/config.go:1022`），Validate 对"仍为默认值"不报错——iPad 通过域名（如 `https://tutor.example.com`）访问 `/rt` 时 WebSocket 握手会被 Origin 白名单静默拒绝，而 operator 若只照抄 example 配置不会得到任何警告。13.3 的家庭入口正是 /tutor/，这是生产部署的第一个踩坑点。
**Fix:** 在 `rt:` 段补注释行（仿 ws 段）：

```yaml
  # Origin whitelist. Defaults to localhost/127.0.0.1 for dev. PRODUCTION
  # MUST set the certificate domain here (IN-03: match scheme+host+port),
  # e.g. allowedOrigins: [tutor.example.com]
  # allowedOrigins: [localhost, 127.0.0.1]
```

### IN-04: home-entry.spec 的 git working-tree 断言在非 git 环境会崩溃而非跳过

**File:** `tests/e2e/home-entry.spec.js:57-67`
**Issue:** 第三个 test 用 `execFileSync('git', ...)` 断言 fallback 页源码零改动。在打包发布产物、无 `.git` 的流水线中执行该套件时，`execFileSync` 直接抛 ENOENT 使整个 spec 崩溃（而非该 test 失败/skip），并可能拖垮同文件其余 test 的报告。该断言本质是开发机守护，不属于行为测试。
**Fix:** 用 `fs.existsSync(path.join(REPO_ROOT, '.git'))` 守卫：非 git 环境显式 `test.skip`，或捕获 ENOENT 输出明确跳过原因。

### IN-05: 崩溃窗口内的行会显示「历史记录」而非「待核实」（unknown 的误归因）

**File:** `pkg/rt/check.go:615-652`（receipt Begin 的时机）+ `pkg/web/static/js/parent-lessons.js:305-317`（unknown→历史记录注记）
**Issue:** `finishCheckSubmit` 中 receipt `Begin` 在 `CompleteCheck`（stage=submitted 落库）之后的同一 goroutine 里执行，两步之间存在一个非原子的崩溃窗口：进程在该窗口内退出，会留下"stage=submitted（completed）+ 无 receipt 行"的 lesson。家长端对 completed 行的 `save_status=unknown` 会渲染「保存状态未知 + 历史记录」注记——把它归因为"回执机制之前的旧数据"，而真实语义恰是 phase 主打的「待核实」（已提交、结果未证实）。窗口为毫秒级且失败方向保守（unknown 不会谎报成功），故仅记录不阻塞。
**Fix:** 长期方案是 `CompleteCheck` 与 `Begin` 同事务或让 `Begin` 前移（受 store 单事务边界限制，Phase 15 对账时统一处理）；短期可在 defer 窗口语义文档化时注明该已知盲区。

## 审查过程中核实为无问题的高风险点（供复核参考）

- **白名单泄漏线**：类型结构（`lessonListItem` 无词面字段）+ 序列化层短路（in-progress 直接 `writeJSON(w, item)`）+ 完成判定与 turn.go 分支表对齐 + httptest 精确键集断言 + e2e 序列化 DOM 负向扫描，五层一致，未找到泄漏通道。
- **receipt bypass**：四处挂载逐一核对，失败路径只发 `EventError(at=save_receipt)`；`TestSaveReceiptFailureIsBypass` 证明 review_result 与 SubmitReview 次数与无回执世界逐字节一致。
- **rt.forceStudentMode**：单点裁决（`handleSessionInit` 的 mode 赋值）短路正确；`tm.mode` 是唯一消费源；`bindEnvForAllLeaves` 已含 `rt.forceStudentMode`；Validate 正确地不新增拒绝分支；测试覆盖 force×test/student 四分支。
- **「回首页」时序**：`pendingHomeButton` 只由三种自然结束 reason 置位、`releasePlaybackResources` 的 `playbackResourceReleased` latch 保证 append 恰好一次且晚于音频释放、start 流程同站重置两个 latch——与 home-button.spec 的正/负断言一一对应。
- **家长前端安全**：parent-lessons.js 全部 `createElement` + `textContent`，无 innerHTML；lesson id 进 URL 走 `encodeURIComponent`；后端 `validLessonID` 白名单（长度/空白/路径分隔符）与 `infra.RTConfig` 口径一致。
- **并发**：receipt 双计数靠 store 层 `WHERE status='pending'` 与 `CompleteCheck` latch 幂等保护；并发 `uncheckedCloseFallback` 的第二次调用落在 Idempotent 分支（零回执零重写）。
- **撤回的假阳性**：学生 summary「对了 X 个」（`check.go:586-591` 全量计数）与家长端 manual-only（`store.go:477-486`）经推演在所有可观察场景数值一致（提交门保证提交时刻全 manual；含 manual=false 的 fallback 路径不播 summary），不构成缺陷。
