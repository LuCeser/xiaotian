# Phase 13.1: Code Review Report

**Reviewed:** 2026-10-09
**Depth:** standard
**Files Reviewed:** 37
**Status:** issues_found

## Summary

Phase 13.1 delivers the three-stage dictation lesson (dictation → check stage with per-word manual verdicts / photo OCR prefill → one unified FSRS submit), server-side word masking, practice-mode isolation, and the 13.1-08 idempotency latches against cross-connection double submits.

The core correctness machinery held up under adversarial tracing. The `tool_requests` PK claim + optimistic version lock + `stage='checking'` latch in `pkg/lesson/executor.go` are mutually exclusive and transactional; the U-2 stale-record purge is sound; the cross-connection double-submit paths (`check_submit_latch`, `correction_submit_latch`, `enter_check_submitted`) are correctly gated and covered by the integration tests in `turn_integration_test.go`. The OCR-prefill-vs-manual-verdict race is genuinely protected by the optimistic lock (a late prefill always conflicts against a landed manual verdict and is dropped via `manualVerdictFor`). Photo chunk sizing (32 KiB raw → ~43.7 KB base64 + JSON overhead) stays under the 65551-byte read limit with margin. SQL is parameterized throughout; the page holds the createElement/textContent XSS discipline; no secrets in code (MIMO_API_KEY is env-only). `tm.tutor` is never set back to nil (grep-verified), so the unguarded dereferences in the check handlers are safe.

What did not hold up: the **losing side of a submit race still hangs in three branches**. 13.1-08 fixed the loser-UI unlock for the main-path latch branch (terminal signal + `submitPending` reset), but the `check_submit` **conflict** branch and **both** practice submit branches send no client-visible terminal signal — the student's submit button shows 「正在提交…」 until they think to tap 结束 or reload. Two further warnings: the completion banner renders a nonsensical 「今天的 0 个词都默写完了！」 on any completion path that never opened a check panel in that session (completed-lesson reconnect, `enter_check_submitted` short path), and the client never closes the previous WebSocket before reconnecting, leaking a server session per retry on the degraded paths.

**Excluded from review (per scope notes):** binary test fixtures under `tests/e2e-rt/real/fixtures/` (`.wav`/`.jpg`) — binary, not reviewable source. The `submitCorrections` unchecked re-read TOCTOU (FA-GAP08-TOCTOU) is a named accepted residual for 13-13 and is not re-reported.

## Critical Issues

None found. The idempotency/latch design, the rating matrices (single reference point discipline), the masking boundaries, and the isolation config all verified clean against their stated contracts.

## Warnings

### WR-01: Submit-race loser paths leave the client UI stuck — no terminal signal in three branches

**File:** `pkg/rt/check.go:532-545` (handleCheckSubmit conflict branch); `pkg/rt/practice.go:366-377` (submitPractice Idempotent latch branch); `pkg/rt/practice.go:351-364` (submitPractice conflict branch)
**Issue:** The client clears `check.submitPending` only on `review_result` or `session_ended` (`pkg/web/static/tutor/index.html:607-620, 660`). 13.1-08 correctly sends `session_ended(lesson_complete)` + `internalClose` on the main path's **Idempotent** latch branch (`check.go:549-574`), but three sibling branches return after only a server-side `recorder.Emit` — no message reaches the losing connection:

1. `handleCheckSubmit` **conflict** branch: reachable when another writer bumps the version while the row stays `checking` (a second tab applying a verdict, or the same session's async voice-verdict goroutine landing between the gate read and `CompleteCheck`). The loser gets no error, no terminal signal — and because the branch never resyncs `tm.tutor.version`, a blind client retry would conflict again.
2. `submitPractice` **Idempotent** branch: the practice latch already fell elsewhere; unlike the main path, no `session_ended` and no `internalClose` — the practice loser's button hangs at 「正在提交…」 indefinitely.
3. `submitPractice` **conflict** branch: same shape as (1).

In all three the student's only escapes are tapping 结束 (not obvious) or reloading. This is exactly the stuck-UI class the phase's own 13.1-08 work (commit `62e579b` "terminal submit unlock") set out to eliminate.
**Fix:**
```go
// check.go handleCheckSubmit conflict branch — align from the stored truth
// (mirroring handleCheckVerdict's conflict path) and tell the family:
if errors.As(err, &conflict) {
    if l, gerr := tm.exec.GetLessonState(context.Background(), lessonID); gerr == nil {
        tm.mu.Lock()
        tm.tutor.align(l.CurrentIndex, l.Version)
        tm.tutor.resyncCheck(l)
        tm.mu.Unlock()
    }
    // A coded, recoverable notice; the client error handler must clear
    // check.submitPending and re-render so the button is tappable again.
    tm.sendError(s, ErrCodeProviderFailed, checkStoreFailedNotice, true)
    return
}
```
```go
// practice.go submitPractice Idempotent branch — mirror the main path's
// loser shape exactly (the row IS submitted, so lesson_complete is honest):
tm.recorder.Emit(EventError,
    infra.F("code", ErrCodeDuplicateSubmit),
    infra.F("duplicate", "practice_submit_latch"))
_ = s.SendControl(SessionEndedMsg{Type: TypeSessionEnded, Reason: ReasonLessonComplete})
tm.recorder.Emit(EventSessionEnd, infra.F("session_id", tm.session))
tm.internalClose()
return
```
Client side (`index.html` error handler): on a recoverable submit-class error, clear `check.submitPending` and `renderCheckPanel()` so the gate re-opens.

### WR-02: Completion banner fabricates 「今天的 0 个词都默写完了！」 on panel-less completions

**File:** `pkg/web/static/tutor/index.html:253`
**Issue:** `showEndingBanner('lesson_complete')` builds the N-words copy from `check.words.length`, which is populated only by `check_started`. Two reachable completion paths never send `check_started` to that connection:

- completed-lesson reconnect: `startCompletedSession` (`pkg/rt/turn.go:602-618`) answers `session_ready` → `session_ended(lesson_complete)` directly (integration test `TestLegacyCompletedStillShortCircuits` pins this exact sequence);
- the `enter_check_submitted` duplicate short path (`pkg/rt/check.go:346-355`).

In both, `resetCheckState` (wired to `session_ready`) has emptied `check.words`, so the banner reads 「今天的 0 个词都默写完了！真棒！」 and offers 再练一组 — nonsense copy shown to a child/parent on a normal reconnect.
**Fix:** fall back to the session's lesson view, which `session_ready` always populates:
```js
if (reason === 'lesson_complete') {
  var n = check.words.length || lesson.words.length;
  p.textContent = '今天的 ' + n + ' 个词都默写完了！' + (check.resultText || '真棒！');
  ...
}
```

### WR-03: Reconnect opens a second WebSocket without closing the previous one — server session leak on degraded paths

**File:** `pkg/web/static/tutor/js/rt-client.js:320-326`; `pkg/web/static/tutor/index.html:738-774, 639-646`
**Issue:** `RTCClient.connect` assigns `this.ws = ws` unconditionally — the previous socket, if still `OPEN`, is orphaned (its `onclose` later fires `stopEverything`, disabling the just-started session's UI state). The start flow never calls `client.close()` first. This bites on every error path that leaves the socket open while re-enabling the start button — notably `lesson_unavailable` (`index.html:639-646` re-enables 开始上课 while the connection stays up): each retry dials a fresh `/rt` connection and the abandoned server-side `TurnManager` lives until transport teardown. On the 1C/1G VPS every idle connection is a goroutine plus read/write buffers, and the orphan's `onclose` can also fire `stopEverything()` mid-new-session, disabling the start button of the session the student just began. Related dead-end: `voice_unavailable` (`recoverable=false`) leaves `started=true` / start button disabled with the socket open — only a reload recovers.
**Fix:**
```js
// RTCClient.connect — drop the previous socket first:
if (this.ws && (this.ws.readyState === 0 || this.ws.readyState === 1)) {
  try { this.ws.onclose = null; this.ws.close(); } catch (e) { /* already closing */ }
}
```
and in the page's `lesson_unavailable` error branch, `client.close()` before re-enabling the start button (plus re-enable the start button on the fatal `voice_unavailable` class so the page states its reason without dead-ending).

## Info

### IN-01: Client-supplied `check_verdict` request_id shares the global `tool_requests` PK namespace with server-derived tool keys

**File:** `pkg/rt/check.go:399-400`; `pkg/lesson/executor.go:576-582, 975-1031`
**Issue:** The verdict handler passes the client's `request_id` verbatim to `ApplyVerdict`, and that string is the PRIMARY KEY of `tool_requests` across all tools. A hand-crafted client could claim a server-derived key (e.g. `<lessonID>-enter-check` or `<lessonID>-complete-check`) as a verdict request_id; the later real tool's replay path would then unmarshal the foreign stored result JSON into the wrong result struct (`Stage:""`, `NewVersion:0`). Impact is confined to the misbehaving client's own session (single-family deployment; every other server-side validation holds and no data crosses connections), so this is hardening, not a vulnerability. The legitimate page (`requestUID()`) can never collide.
**Fix:** prefix server-derived idempotency keys (e.g. `srv-<lessonID>-enter-check`) or namespace the `tool` column into the replay lookup so cross-tool replay of a claimed key is structurally impossible.

### IN-02: `session_ended` clears `check.submitPending` but skips the re-render on the terminal-drain path

**File:** `pkg/web/static/tutor/index.html:660, 675-679`
**Issue:** After a `playback_ack_timeout` while a submit was pending, the handler resets `check.submitPending` and then returns early (`terminalDraining`) without `renderCheckPanel()` — the button keeps showing 「正在提交…」 even though the state cleared. Cosmetic only (the next render would disable it via the `terminalDraining` gate, but no next render comes on that path).
**Fix:** move `renderCheckPanel()` above the `if (terminalDraining) return;` branch, or call it in the drain branch too.

### IN-03: Driver shadows the global `URL` constructor

**File:** `tests/e2e-rt/real/driver-rt-lesson.mjs:91`
**Issue:** `const URL = process.env.E2E_RT_URL || 'ws://127.0.0.1:8790/rt'` shadows the WHATWG `URL` class for the whole module. Only string methods are used today, so nothing breaks — but a future `new URL(...)` in this file fails confusingly.
**Fix:** rename to `RT_URL` (or `const RT_URL = URL` and drop the shadow).

### IN-04: Correction finish stores the pre-`ClearUnchecked` version into the session cache

**File:** `pkg/rt/check.go:855`
**Issue:** `finishCorrections` sets `tm.tutor.version = in.version` (the version read before the correction writes). When `ClearUnchecked` succeeded, the row is now at `in.version + 1`, so the in-memory cache disagrees with the store at session end. No consumer exists — the session ends immediately and any later session resyncs from the row — but it leaves a misleading value behind for anyone who later extends the correction path.
**Fix:** capture the `ClearUnchecked` result's `NewVersion` and store that (or drop the assignment; the session is closing).
