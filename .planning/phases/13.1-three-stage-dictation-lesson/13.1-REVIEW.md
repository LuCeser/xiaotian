## Critical Issues

### CR-01: handleCheckSubmit 忽略 CompleteCheck 的 Idempotent 结果，跨连接竞争会二次提交 FSRS review

**File:** `pkg/rt/check.go:507-543`
**Issue:**
`Executor.CompleteCheck` 的返回值里 `Idempotent` 标记"这次调用没有真正落闩锁"（两种来源：同 request_id 重放存储结果 `executor.go:851-855`；或 `checking→submitted` 闩锁已被别人落下时的 latch replay `executor.go:899-909`）。`TestCompleteCheckGate`（`executor_test.go:463-529`）证明存储层对第二次提交是安全的——但 /rt 回合管理器拿到 `err == nil && res.Idempotent == true` 后**没有任何分支**，直接走 `finishCheckSubmit` → `tm.cfg.Words.SubmitReview`（`check.go:543, 568`）。

单连接场景是安全的：`HandleControl`/`Close` 都在 transport 读循环上串行执行（`pkg/rt/conn.go:303-320`），第一次 submit 返回时 `checking` 已被同步置 false，重放帧会被 `!checking` 分支挡住。但 lesson row 是**进程级共享**的（r0-YYYYMMDD 每日同一行；多标签页/重连场景是 13.1-04 明确支持的形态）：第二个连接的 TurnManager 各自持有 `checking=true` 的 tutor，双方都过人工闸后先后 check_submit——输家的 `CompleteCheck` 返回 latch replay（`Idempotent=true, err=nil`），照样发起第二次 `SubmitReview`。这直接违反 T-13.1-01 的冻结不变量："ONLY its first commit may drive the one FSRS review write"。同一份代码里另外两个调用方都做了正确防守：练习路径 `submitPractice`（`pkg/rt/practice.go:366-377`）显式检查 `res.Idempotent` 后返回；close 兜底 `uncheckedCloseFallback`（`check.go:847-851`）同样检查——唯独主提交路径漏掉。

后果：同一批词的 review 被提交两次（第二次大概率被 python 侧按"当日已复习"吞成 Missing，最坏情况写入重复 review_logs 行），第二个学生听到错误的"保存 0/N"+失败后缀总结，且事件流出现两条 `review_submitted` 审计记录。

**Fix:**
在 `handleCheckSubmit` 的 `CompleteCheck` 成功返回后、组装评分前加一个与练习路径对称的守卫：

```go
res, err := tm.exec.CompleteCheck(ctx, lessonID, expected, m.RequestID, false)
if err != nil { /* 现有 conflict / store-failure 分支不变 */ }
if res.Idempotent {
    // 闩锁已被别的连接落下（或同 request_id 重放）：绝不发第二次
    // SubmitReview。对齐存储态即可；本会话若还没见过 review_result，
    // 回一条只读的既有结果或保持静默（与 submitPractice 同纪律）。
    tm.mu.Lock()
    tm.tutor.version = res.NewVersion
    tm.tutor.checking = false
    tm.mu.Unlock()
    tm.recorder.Emit(EventError,
        infra.F("code", ErrCodeProviderFailed),
        infra.F("duplicate", "check_submit_latch"))
    return
}
```

同时建议补一条跨连接回归测试：两个 TurnManager 共享同一 lesson row，先后 check_submit，断言 fake word source 恰好收到 1 次 `SubmitReview`（现有测试全部单连接，`turn_integration_test.go` 只有 1 处 `NewTurnManager` 调用，该场景零覆盖）。

## Warnings

### WR-01: 前端 check 面板跨课不重置，旧课的检查面板在新课听写期间仍然可点

**File:** `pkg/web/static/tutor/index.html:172, 472-482, 535-548`
**Issue:**
`check` 对象（`active/words/verdicts/ocr/submitPending/resultText`）只在 `check_started` 到达时重置；`check.active` 从未被置回 false，`#rt-check` 面板也只在 `renderCheckPanel` 内部因 `!check.active` 才隐藏。`session_ready` 处理器（index.html:472-482）隐藏了 banner 和 notice，却没有碰 check 状态。于是上一节课结束后（lesson_complete 或练习结束）再点「开始上课」/「再练一组」进入新课，旧词表的 check 面板（含对/错按钮和提交键）仍挂在页面上并可交互：新课听写期间点它会向服务端发 `check_verdict`/`check_submit`，服务端按 `checkStageClosedNotice`（「这一课已经检查完了哦」）逐条拒绝（`pkg/rt/check.go:351-364, 416-440`），错误面板被反复点亮，孩子会看到令人困惑的报错；`window.__rtTutor.observe().check` 的口径也随之失真。无数据损坏（服务端校验兜住了），但属于可稳定复现的状态泄漏。

**Fix:**
在 `session_ready` 处理器里随 banner/notice 一起重置检查状态：

```js
client.on('session_ready', function (m) {
  // ...现有逻辑...
  check.active = false;
  check.words = [];
  check.verdicts = {};
  check.ocr = {};
  check.submitPending = false;
  check.resultText = '';
  $('rt-check').hidden = true;
});
```

### WR-02: enterCheck 冲突恢复路径不区分"行已被提交"，会给已在 submitted 的行广播 check_started

**File:** `pkg/rt/check.go:315-341`
**Issue:**
`enterCheck` 的 `EnterCheck` 冲突分支只做"从存储真值对齐"（`align` + `resyncCheck`），随后**无条件**继续 `EventCheckStarted` + `CheckStartedMsg(reason=dictation_done)` + bridge 播报。`resyncCheck`（`pkg/rt/dictation.go:479-486`）在行已是 `submitted` 时会把 `checking` 置 false、`completed` 置 true，但消息照发——学生拿到一个打不开的检查面板，之后每个对/错点击都被"这一课已经检查完了哦"拒绝。触发窗口很窄（需要第二个连接在本连接 AdvanceWord 首提交与 EnterCheck 之间完成 EnterCheck→verdict→submit 全链路），但多标签页是 WR-01/CR-01 同族的真实形态，且失败表现是"死面板"而非可见的诚实降级。

**Fix:**
冲突对齐后检查同步出的阶段，已 `submitted` 时改走完成短路径（发 `SessionEndedMsg{Reason: ReasonLessonComplete}` + `internalClose()`），不广播 check_started：

```go
tm.mu.Lock()
tm.tutor.align(l.CurrentIndex, l.Version)
tm.tutor.resyncCheck(l)
alreadySubmitted := l.Stage == lesson.StageSubmitted && !tm.tutor.correction
tm.mu.Unlock()
if alreadySubmitted {
    _ = s.SendControl(SessionEndedMsg{Type: TypeSessionEnded, Reason: ReasonLessonComplete})
    tm.internalClose()
    return
}
```

### IN-03: ocr.go 中两个完全相同的正则重复定义

**File:** `pkg/ocr/ocr.go:187, 232`
**Issue:** `textPattern` 与 `wordEntryPattern` 是逐字符相同的 `regexp.MustCompile`（`"text"\s*:\s*"((?:[^"\\]|\\.)*)"`），双份编译与维护点。
**Fix:** 合并为一个 `textPattern`，两处解析共用。

### IN-04: pickPracticeWords 把 n<=0 当"不限量"

**File:** `pkg/rt/practice.go:109`
**Issue:** `if n > 0 && len(avail) > n { avail = avail[:n] }`——n 为 0/负数时返回全词表（仅扣当日排除集）。当前唯一调用方传常量 `practiceWordsLimit(10)`，无实际触发，但语义是个暗坑。
**Fix:** 在函数入口对 `n <= 0` 直接返回 `nil`（或文档化 n<=0 语义并加防御断言）。

### IN-05: handleSessionInit 不拒绝同一连接上的第二次 session_init

**File:** `pkg/rt/turn.go:461-552`
**Issue:** 协议未声明 session_init 的一次性，处理路径也没有 `tm.closed`/已初始化守卫：完成短路径（`startCompletedSession` → `internalClose`）之后再来的 session_init 会再次走完整初始化并在已关闭会话上重发 session_ready/session_ended。当前客户端不会重发，属低概率健壮性缺口。
**Fix:** `handleSessionInit` 入口检查 `tm.tutor != nil || tm.closed` 时回 `invalid_message`（recoverable）。

### IN-06: mock 服务器练习分支缺重复提交重放守卫

**File:** `tests/e2e-rt/mock-rt-server.js:1050-1077`
**Issue:** 通用重放闸是 `if (state.reviewResults > 0) break`（1056），而练习分支刻意保持 `reviewResults` 为 0（1070 `state.reviewResults += 0`，作为"无 FSRS 写"的 wire 证据）——于是练习路径的第二次 `check_submit` 会再发一条 `review_result` + 再播一遍总结，违背该文件头部声称镜像的 Pitfall 6 契约。现网无 spec 触发此路径，属 mock 与真服务端的镜像偏差。
**Fix:** 练习分支改用独立闸（如 `if (state.practiceSubmits > 0) break;`），保持 `reviewResults` 语义不变。

### IN-07: driver 的 `rejectUnauthorized: false` 是无效冗余项

**File:** `tests/e2e-rt/real/driver-rt-lesson.mjs:884-887`
**Issue:** L3 隔离实例是明文 `ws://127.0.0.1:8790`，该 TLS 选项没有实际作用，却容易被误读为"允许对生产自签证书"，与文件里 U-1 防复发的严肃口径不符。
**Fix:** 删除该选项，或加一行注释说明它只对 wss 生效且本层永远不用。
