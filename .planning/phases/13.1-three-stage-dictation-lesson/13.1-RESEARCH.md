### Locked Decisions

（逐字复制自 `13.1-CONTEXT.md` `<decisions>`，规划必须逐条遵守）

**课堂模型（三段式）**
- **D-01:** 「好了/可以了/下一个」只表示「这个词已经默写了」（完成信号），不代表写对。全部词默完、播报完后才进入检查阶段。推翻现行「confirm→good」的行为评级语义。— Reversibility: costly — 完结写路径、总结话术、时序事件与既有单测都要随模型改写，回退需再改一遍。
- **D-02:** 统一提交评级表：**检查对＋无提示=good；检查对＋有提示=hard；检查错=again**（检查结果优先于行为，提示次数作降档因子）。与 U-9 裁定（hint 后写对=hard、仍错=again）同一张表。
- **D-03:** 超时未检查的课按行为**降一档**落库：无提示说好→hard、有提示→again，课行带「未核对」标记；事后补拍照可修正评级。
- **D-04:** 完结总结挪到检查＋提交之后播报（内容含对错战果，如「今天 7 个词对了 5 个」），不再是现在这种无对错信息的空总结。

**检查阶段**
- **D-05:** 拍照 OCR 为主路径，**人工校正层必经不可省**——前提是任何 OCR/多模态模型都必然认错，必须能处理「默对了识别成错」和「默错了识别成对」两类。
- **D-06:** 人工校正两条输入路：① 屏幕逐词显示后点「对/错」；② 语音说（「第一个词对了」「apple 现在写在纸上的是 aple 而不是 apple」）——语音校正可携带实际写法，老师可接话教学。OCR 判错被人工改判覆盖，提交的评级以人工改判为准。
- **D-07:** 检查完成后**一次性统一提交** FSRS（非逐词多次写）；提交仍以 pybridge 实际 Updated 集合如实报告，部分/零更新不冒充全部成功（13-CONTEXT 口径延续）。

**界面口径（测试/学生双模式）**
- **D-08:** URL 参数切换，**默认学生模式**；测试模式（如 `/tutor/?mode=test`）保持现状（词全显＋trace）。iPad 书签天然指向学生模式，孩子永远遇不到全显词表。
- **D-09:** 学生模式词表三态：未默=序号占位、当前词=序号高亮（**不显词文本**，纯语音报词）、已默=**显词＋绿勾**；检查阶段逐词展开。
- **D-10:** 对话区双列 trace（老师左、学生右、学生识别文本常驻）**两种模式都有**，作为家长回放的最小形态。学生模式默写阶段**目标词打码**：老师报词字幕显「第 N 个词」不显词、学生识别文本中的目标词替换为 •••；进入检查阶段解除打码、完整回溯。防泄题原理：听写的答案就是拼写，屏幕文字天然带拼写（报词字幕、问词义的识别文本、跟读上屏都会泄）。— Reversibility: costly — 打码变换横跨服务端字幕与前端渲染两处，回退要同时拆。

**再练一组（U-5）**
- **D-11:** 完结/无到期词后出现「再练一组」入口：从词库**随机**抽词、**避开当日已默**、≤10 不足全给（与正常课同量级），同样走三段式流程。
- **D-12:** 练习结果**单独记录**（独立存储/标记），**不进 FSRS 主调度**——同日重复练习不扭曲调度（现用 fsrs 库对同日二次复习支持弱）；家长可查，后续想转正有数据。— Reversibility: reversible — 存储层决策，转正只需迁移练习记录。
- **D-13:** 状态区分文案：「今天的 N 个词都默写完了」＋「再练一组」按钮 vs「词库暂无到期词，下次复习在 X 天后」——两条收尾路径不再共用一套完成话术。

**执行顺序**
- **D-14:** **三段式先行**：第一层缺陷修复（U-9、U-2、E2E 隔离，已完成 ✅）→ Phase 13.1 → 13-13 VPS 部署＋正式验收。第一周检查（2026-10-07）记未达成；第三周 2026-10-21 前须完成 13.1＋13-13。

**显式取代**：13-CONTEXT 的「完结总结先按 pybridge 实际 Updated 集合写学习记录，再完整播报后结束」条款——本阶段把写学习记录挪到检查之后统一提交；其余 13-CONTEXT 口径（状态机模型、ACK 证据门、幂等推进）继续有效。

**不动**：实时链路（采集/VAD/ASR/LLM 意图/TTS/打断）、服务端状态机的课堂节奏裁量权、pybridge/FSRS 调度器本身、13-13 部署范围、E2E 隔离规范。

## Summary

本阶段是对 Phase 13 已交付的 `/rt` 默写状态机的一次**模型升级**：把「说『好了』即按行为写评级」改为「说『好了』只记行为 → 全部写完进入检查阶段（拍照 OCR 逐词比对＋人工必经校正）→ 一次性统一提交 FSRS → 含对错战果的总结」。研究确认：**U-9 评级矩阵已在码上落定且注释明确预留了本阶段的接缝**——`wordRating(outcome, hints)` 是唯一矩阵引用点，注释写明「13.1 的未核对兜底路径必须走这个函数、不得分叉第二份矩阵」[VERIFIED: pkg/rt/dictation.go:110-135]。检查阶段的评级函数是它的直接扩展：以「检查结果」替换「行为 outcome」作为输入即可，无需新矩阵。

三个关键架构发现：**（1）学生模式的词泄露面在服务端**——`session_ready.lesson.words` 把全部词明文发给页面（pkg/rt/protocol.go:169-179），`teacher_sentence` 字幕与 `transcript` 也带明文词（pkg/rt/turn.go:1180-1182、turn.go:884），只做前端渲染隐藏属于「 cosmetic 打码」，服务端发送侧变换是结构性方案（D-10 的 costly 可逆性注记本就预期两层）；**（2）逐词行为数据目前只在内存**——`perWordOutcome/perWordHints` 是 `DictationTutor` 内存字段（pkg/rt/dictation.go:189-190），课行（lessons 表）只落 current_index/version（pkg/lesson/store.go:41-49），检查阶段要跨断线存活就必须把阶段态与逐词判定持久化到 Go 自有表/列；**（3）已完结课行目前一律短路结束**——`CurrentIndex >= len(Cards)` 直接 ready＋ended（pkg/rt/turn.go:451-452），「事后补拍照修正评级」需要一条「带未核对标记的课行重进检查阶段」的新恢复路径。可复用资产充足：`pkg/grading.GradeWord`（归一化＋Damerau-Levenshtein＋逐字符 diff）就是逐词比对引擎，`pkg/ocr.Pipeline`＋MiMo ChatVision 是识别管线（旧页 photo-controller 的 file-input 拍照＋32KiB 分块＋1MiB 上限模式可整体移植到 `/tutor/`），幂等写走 `pkg/lesson` 既有 request_id＋expected_version 框架。

**Primary recommendation:** 服务端状态机新增 `checking` 阶段（课行持久化 stage＋逐词判定）；学生模式打码在服务端发送侧做（session_init 带模式，字幕/转写/词表按模式脱敏，进检查阶段下发全量词实现「解除打码、完整回溯」）；逐词比对复用 `pkg/grading`＋`pkg/ocr`（OCR 提示词加数组变体）；统一提交复用 `WordSource.SubmitReview` 且只调一次；「再练一组」走 Go 自有练习记录表（不碰 Python 所有权的 review_logs）。

### Pattern 1: 检查阶段评级 = wordRating 的兄弟函数（单一矩阵纪律）

**What:** D-02 表（检查对＋无提示=good／检查对＋有提示=hard／检查错=again）与 D-03 表（未核对：无提示→hard、有提示→again）都是「(结果, 提示次数) → 评级」的纯函数。U-9 已落码的 `wordRating(outcome, hints)` 注释明确：「Phase 13.1 single reference point: the UNVERIFIED fallback path (photo check absent) MUST rate through this function — 13.1 must not fork a second matrix. The "没听清提示/多音字" human-synthesis wording stays a 13.1 concern; this (outcome, hints) signature is the entire reserved seam for it.」[VERIFIED: pkg/rt/dictation.go:110-115]

**When to use:** 检查完成时的统一评级用 `checkRating(checkResult, hints)`（新纯函数，表驱动可测）；超时未核对兜底直接调用既有 `wordRating(outcome, hints)`——降一档语义恰好就是现行矩阵（confirmed+0hint=good→降 hard 即 timeout 无提示分支的值；注意兜底是「按行为查表后整体降一档」，不是复用 timeout 行，见 Pitfall 1）。

**Example:**

```go
// 检查结果词汇（建议常量，规划定名）：
// checkCorrect = "correct"   // 检查对（OCR 或人工改判后）
// checkWrong   = "wrong"     // 检查错
func checkRating(result string, hints int) string {
    switch result {
    case checkCorrect:
        if hints > 0 { return ratingHard }  // ratingHard = "hard"
        return ratingGood                    // ratingGood = "good"
    case checkWrong:
        return ratingAgain                   // ratingAgain = "again"
    default:
        return "" // 未检查/无效 → 不在此函数处理（走 D-03 兜底）
    }
}
```

### Pattern 2: 学生模式打码——服务端发送侧变换＋检查阶段全量揭示

**What:** 模式随 `session_init` 上行（URL 参数由页面读后传入）；服务端在**发送侧**按模式变换三类载荷：① `LessonView.words` 未默词位置发占位（或空串）；② `teacher_sentence.text` 报词句产「第 N 个词。」不产词文本（greeting/announce 模板函数已是纯函数，变换点内聚：dictation.go:503-513）；③ `transcript.text` 中目标词替换 •••。逐词提交/揭示时下发新消息（词＋绿勾态）。进检查阶段时服务端一次性下发全量词表（`check_started` 载荷），客户端据此回溯解密 ••• 与占位——「解除打码、完整回溯」（D-10）无需重放历史消息。

**Why server-side:** 打码目标是「孩子看屏幕泄题」；前端方案下词明文仍在线上与 DOM，任何控制台/抓包可见，且与 D-10「打码变换横跨服务端字幕与前端渲染两处」的可逆性预期一致。注意打码只作用于**外发副本**：`processTurn` 先发 transcript 再分类（turn.go:884-889），打码必须只动 `SendControl` 的消息体，绝不动喂给 `classifyTurn` 的原文。

### Pattern 3: 照片上传 = 旧页已验证模式移植到 /rt

**What:** 客户端 `<input type="file" accept="image/*" capture="environment">`（iPad Safari 标准相机路径，无需 getUserMedia、无需 HTTPS 前置授权——旧页生产在用）→ canvas 压缩阶梯（1600px@q0.8 → … → 1024px@q0.5，止于 ≤768KiB）→ 32KiB 分块 → 服务端装配（voice.Buffers 同款，上限 `PhotoConfig.MaxImageBytes` 默认 1MiB）→ `ocr.Pipeline.Process`（JPEG SOI 校验＋ChatVision＋置信度门）。[VERIFIED: pkg/web/static/js/photo-controller.js:10-36; pkg/infra/config.go:350-379]

**/rt 侧差异:** `/rt` 单消息读上限 65551 字节 [VERIFIED: pkg/rt/conn.go:22-26]，音频二进制帧无通道前缀——图片通道需要轻量判别（如二进制帧首字节通道号，或新的分块控制消息），并保留「取消/重拍清空装配缓冲」纪律（photo_cancel 的教训：不丢弃则下一张的序号被当重复吸收，cmd/service/photo.go:248-258）。

### Pattern 4: 检查阶段写路径 = request_id＋expected_version 幂等

**What:** 逐词改判（点按/语音同路径）、检查提交都带 request_id 走 tool_requests 去重＋课行乐观锁；重复点按/重试回放首次结果。统一提交必须**一次性**（D-07）：以课行 stage 迁移（checking→submitted）作幂等闸，第二次提交请求回放首次结果而非再次 RunReview——否则产生双 review_logs 行且 FSRS 按最后一次重排（见 Pitfall 7）。

### Anti-Patterns to Avoid

- **在前端隐藏词当打码**：词明文仍在线上/DOM；D-10 要求两层，服务端是权威层。
- **为检查阶段新写一套比对/归一化**：`pkg/grading.Normalize`（大小写＋语言感知去标点）是唯一归一化权威 [CITED: pkg/grading/grading.go:98-101 注释]，绕开它会造成两处口径漂移。
- **LLM 判对错**：判对错只来自 OCR＋人工改判；LLM 在检查阶段仍只做意图分类（CONTEXT Established Patterns 锁定）。
- **Go 直写 review_logs/cards**：违反 ADR-2026-08-01 写分离（跨系统写禁止）。练习记录用 Go 自有新表。
- **练习选词走 RunDue**：会取 fetch lock 且只返回到期词（刚默完的词不再到期）；随机抽词用 CardRepository 读＋Go 侧采样。
- **检查阶段播报绕过 sentence_ack 门**：CONTEXT 明文「检查阶段逐词引导播报同样过 ACK 门，不因新阶段绕过」。

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 逐词对错判定 | 自写归一化＋编辑距离 | `grading.GradeWord(expected, heard, lang)` | 已含大小写折叠、中英归一化、Damerau-Levenshtein、near-miss 与字符级 diff；全表测 |
| 手写 OCR | 直调 vision API | `ocr.NewPipeline(mimoReader(...), cfg.Photo.ConfidenceThreshold)` | JPEG 校验、严格 JSON 提示词、宽松解析（prose/代码栅栏容忍）、置信度门全在管线里 |
| 图片上传装配 | 新发明分块协议 | 移植 photo-controller 常量＋voice.Buffers 装配范式 | 32KiB/帧、1MiB 上限、TTL 清扫、cancel 纪律都是踩坑后的定值 |
| 幂等推进/改判 | 时间戳去重、内存去重 | `lesson.Executor` 框架（tool_requests＋乐观锁＋U-2 倒退防护） | 重试安全已在库级证明（含课行重置场景） |

**Key insight:** 本阶段几乎没有「新能力」，全是把四个已验证资产（状态机、比对引擎、OCR 管线、幂等框架）接到一条新流程上——规划的任务切分应按「接线」而非「造轮子」组织。

## Common Pitfalls

### Pitfall 1: 评级矩阵分叉
**What goes wrong:** 检查评级、未核对兜底、练习记录各写一套映射，口径漂移（hint 语义曾经就是这么错的——U-9 之前「终态覆盖」与裁定相反）。
**Why it happens:** D-02 表和 U-9 表形似而输入不同，顺手复制粘贴。
**How to avoid:** 全部走 `wordRating`/其兄弟纯函数；`dictation.go:110-115` 注释是纪律原文。未核对降一档=「行为查表值再降一档」（good→hard、hard→again），明确写成独立小函数＋单测钉死。
**Warning signs:** 任何 rating 字面量 "good"/"hard"/"again" 出现在 dictation.go 的映射函数之外。

### Pitfall 2: 检查阶段态不持久化，断线即丢
**What goes wrong:** 孩子拍完照/改判到一半切后台（iPad Safari 极常见），WS 断开，`DictationTutor` 连同判定全丢；重连时课行 `CurrentIndex >= len(Cards)` 直接 ready＋ended（turn.go:451-452），检查永远做不完，评级却已按 D-03 降档落库。
**How to avoid:** 逐词判定/阶段态落库（课行加列或伴表）；`startCompletedSession` 前先查「未核对」标记→进入检查恢复路径而非短路结束。注意 `perWordOutcome/perWordHints` 目前也要随 advance 提交落库（或从事件流重建），否则断线后兜底评级缺输入。
**Warning signs:** 任何「检查中途刷新页面」的手测场景丢判定。

### Pitfall 3: 学生模式词表仍全量下发
**What goes wrong:** 只在 renderProgress 里隐藏词（index.html:167-183 现全显 `lesson.words[i]`），词明文仍在 `session_ready`、线上、DOM——「打码」名存实亡。
**How to avoid:** Pattern 2；`LessonView` 在学生模式只给已揭示词，未默位发占位；新消息承载揭示。
**Warning signs:** 学生模式页面源码/WS 帧里搜得到未默词。

### Pitfall 4: 打码污染意图分类输入
**What goes wrong:** 把打码后的 transcript 喂给 `classifyTurn`，孩子说「apple 写好了」被 ••• 掉后分类成 chat（U-3 家族的新变体）。
**How to avoid:** 打码只作用外发副本（Pattern 2）；单测断言分类输入＝原文、外发＝脱敏文。
**Warning signs:** 学生模式下确认/提示类意图误判率上升。

### Pitfall 5: 照片通道破坏 /rt 既有二进制契约
**What goes wrong:** 图片不分块顶爆 65551 读上限（连接被断）；或复用裸 PCM 通道导致一张图的字节被当音频喂 VAD/ASR；或重拍后旧分块混入新图（photo_cancel 教训，cmd/service/photo.go:240-258 注释原文记录了该事故形态）。
**How to avoid:** 二进制帧加轻量通道判别或新增控制消息分块；保留装配上限（1MiB）与「提交/取消后清缓冲」纪律；e2e 补「重拍」用例。
**Warning signs:** 拍第二张时 OCR 结果是两张图的混合。

### Pitfall 6: 改判与提交的重复写
**What goes wrong:** 语音改判与点按改判并发（说「第一个词对了」同时手点对）；统一提交被重试执行两次。
**How to avoid:** 全部走 `lesson.Executor` 同框架（RT-07 语义）；提交以 stage 迁移为幂等闸（Pattern 4）。
**Warning signs:** review_logs 同词同日多行（非修正场景）；「对/错」点两次出现两条老师播报。

### Pitfall 7: FSRS 同日二次写的排程副作用
**What goes wrong:** 「事后补拍照修正评级」（D-03）= 对已 review 过的词再次 RunReview——机械上可行（`cmd_review` 无同日守卫，逐词 `SCHEDULER.review_card`＋再插一条 review_logs，[VERIFIED: third_party/python/vocab_manager.py:479-529]），但 FSRS 状态按「最后一次评级」重算，与「一次写对」的排程不同（py-fsrs 短间隔走 learning_steps，本项目配置 learning_steps=(1min,10min)/relearning=(5min)，[CITED: github.com/open-spaced-repetition/py-fsrs]）。
**How to avoid:** 会话内能等到检查就别先写行为评级（默认顺序本就是检查后统一提交）；「先写后修」只发生在超时未核对场景，属用户接受口径（D-03 原文「事后补拍照可修正评级」）。修正写入时在课行/事件里如实记录「系修正」。
**Warning signs:** 把修正当常规双写路径大量触发。

### Pitfall 8: 检查阶段意图词表扩了白名单漏了提示词
**What goes wrong:** 新意图（如判词对错、口述实际写法）加进 `intentWhitelist` 但 `buildClassifySystemPrompt`（dictation.go:610-640）仍是默写阶段八词表＋当前词语境——分类输出永远对不上。
**How to avoid:** 检查阶段的分类提示词单独构建（携带全词表＋逐词判定态）；`parseIntentJSON` 白名单校验保持不变（T-13-13：模型输出不可信）。口述实际写法（「写的是 aple」）需要分类输出携带载荷字段或直接透传原始 transcript 给检查处理器——规划定契约。
**Warning signs:** 检查阶段语音口令大面积落 chat。

### Pitfall 9: 检查阶段播报绕过 ACK 门 / 总结先于提交
**What goes wrong:** 逐词引导播报不等 `sentence_ack` 就推进（抢跑→旧音频复活类缺陷）；或为省事先播「战果总结」再提交——违反 D-04「总结挪到检查＋提交之后」。
**How to avoid:** 检查阶段复用 `runAnnouncement`/`awaitPlaybackCompletion`（ack 驱动 settle，turn.go:577-597）；顺序固定：改判收敛 → SubmitReview（如实 Updated）→ 战果总结 → session_ended(lesson_complete)。
**Warning signs:** 时序 JSONL 里 summary 音频先于 review_written。

### Pitfall 10: 再练一组污染主调度
**What goes wrong:** 练习词走 RunReview（哪怕 again）→ FSRS 同日重排（D-12 明言规避）；练习课行占用 `r0-YYYYMMDD` 主键或被次日恢复逻辑捡到。
**How to avoid:** 练习课行独立 id 命名空间（如 `r0x-…`）＋ kind 标记；结果只写 Go 自有练习表；E2E 隔离课键 `e2e-*` 钉死机制不受影响（docs/E2E-ISOLATION-SPEC.md）。
**Warning signs:** review_logs 出现练习词；次日开工时冒出练习课行。
