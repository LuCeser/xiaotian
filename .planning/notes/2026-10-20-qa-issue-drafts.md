## Issue A：默写任务应按学科隔离，避免语文与英语混合出题

### 问题与影响

词库同时录入语文和英语后，一次默写会交替出现两个学科的内容。原记录描述为“两个英语、两个语文交替”。这使用户无法按单一学科完成一次练习。

### 原记录对应的复现步骤（待当前版本验证）

1. 在词库中同时准备语文和英语内容。
2. 发起一次默写，连续推进多个词。
3. 检查本次出题内容是否跨学科。

原记录未说明发起入口、启动指令，以及是否已经指定学科，需要在复现时补充。

### 期望行为

一次默写仅使用一个学科的内容。用户可以先完成英语默写，再单独发起语文默写。

### 涉及范围

- 发起默写时如何确定学科。
- 根据学科筛选候选词，以及生成本次默写列表。
- 本次任务推进时保持学科一致。
- 指定学科无词或词量不足时的反馈。

### 建议验收条件

- [ ] 词库同时存在两科学习内容时，发起英语默写，全程只出现英语内容。
- [ ] 发起语文默写，全程只出现语文内容。
- [ ] 完成英语任务后，可以单独发起语文任务，且不继承上一任务的出题列表。
- [ ] 所选学科词量不足时，不使用另一学科的内容补足；具体反馈按确认后的规则验收。

### 待确认

- 原问题发生在哪个页面或语音入口，启动时是否已经明确学科？
- 未指定学科时，是询问用户、使用已选学科，还是采用其他规则？
- 词量不足时，是按实际数量开始，还是要求用户先补充词库？

## Issue B：默写中“好了 / 下一个 / 好嘞”等确认语未推进到下一词

### 问题与影响

默写过程中，用户说“好了 / 下一个 / 好嘞”等确认语后，没有进入下一词，系统表现得像是在回应上一句话。用户无法顺畅地通过口语控制默写进度。

### 原记录对应的复现步骤（待当前版本验证）

1. 发起包含多个词的默写。
2. 当前词播报完成后，分别说“好了”“下一个”“好嘞”。
3. 观察是否推进到下一词，还是产生与推进无关的对话回复。

### 期望行为

处于等待用户完成当前词的状态时，上述确认语应触发一次推进，播报下一词。

### 涉及范围

- 语音转写结果是否正确保留用户表达。
- 当前默写状态下，确认语的识别与处理。
- 确认语是否进入普通对话处理，导致推进动作未发生。
- 推进后词序更新及下一词播报。
- 最后一个词确认后的完成行为。

以上为排查范围，不能据此认定具体原因；原记录也未证实这是某次改动引入的回归。

### 建议验收条件

- [ ] 在等待用户确认的默写状态下，“好了”“下一个”“好嘞”均能推进到下一词。
- [ ] 每次有效确认只推进一个词，不重复当前词或跳过词。
- [ ] 确认后发生实际推进与播报，不仅生成口头回应。
- [ ] 最后一个词确认后进入正常完成状态。
- [ ] 非默写状态下，不把这些表达误当成默写推进指令。

### 待确认

- 问题发生在播报中、播报结束后，还是两种情况都有？
- 失败时的语音转写文本、系统回复和任务状态分别是什么？
- 哪个版本或入口可以稳定复现？

## Issue C：默写推进延迟：预先确定词序，并核查逐词推进是否经过大模型

### 问题与影响

默写中说“下一个”后，下一词的响应明显偏慢，影响连续练习。原记录怀疑存在不必要的大模型调用，但尚无调用记录或耗时数据证明。

### 原记录对应的复现步骤（待当前版本验证）

1. 发起一轮 10 个词的默写。
2. 当前词完成后，说“下一个”。
3. 记录从确认语结束到下一词开始播放的时间，并检查各处理阶段的耗时与调用。

### 期望行为与流程约束

- 这轮 10 个词在开始时一次性选定，并确定顺序。
- 普通“下一个”推进直接取本次列表中的下一词，发起所需的音频生成或播放。
- 普通推进使用确定的工作流，不进入 agent loop，不等待大模型重新选词、规划或生成对话回复。

用户表达的“慢也只应慢在 TTS”应作为减少额外等待的目标。实际语音交互仍需分别测量语音结束判定、转写、传输和播放等耗时，不能在未测量前承诺端到端延迟仅来自 TTS。

### 涉及范围

- 初始化时生成并保存本轮词序。
- 逐词推进时读取列表与更新进度。
- 正常推进是否触发大模型或 agent loop。
- 下一词的 TTS 请求或已有音频播放。
- 从确认语结束到开始播放的耗时测量与定位。

本 Issue 不预先要求新增音频缓存或批量预生成；先确认实际耗时及现有能力，再判断是否需要进一步优化。

### 建议验收条件

- [ ] 对一轮 10 词的默写，可验证词条和顺序在开始时已确定。
- [ ] 正常“下一个”推进沿已确定列表执行，不重新选词或重排。
- [ ] 通过调用记录或等效验证，证明正常推进不调用用于规划、选词或对话生成的大模型，不进入 agent loop。
- [ ] 推进确认后直接触发下一词所需的音频生成或播放，无额外的对话等待。
- [ ] 在同一环境下记录优化前后的端到端延迟，并区分语音输入处理、推进逻辑、TTS 与播放等待。
- [ ] 确定可接受的延迟阈值或改善目标后，按该目标完成验收。

### 待确认

- “10 个词”是本次复现场景，还是所有默写任务的固定数量？草案暂按复现场景处理，不修改其他任务的数量规则。
- 当前慢在哪里，是否真的存在大模型调用？
- 使用哪个入口、网络环境和语音服务测量？可接受的延迟目标是多少？
- 自由提问、重复播报等其他指令是否仍需走不同处理流程？本 Issue 的无 agent loop 约束先限定为普通逐词推进。
